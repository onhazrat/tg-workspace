# How Heritrix, BUbiNG, Frontera/Scrapy, Common Crawl and ManifoldCF prioritise crawl work

Method note. Almost everything below comes from reading the source at a pinned commit (shallow clones taken 2026-10-15), plus a few primary documents. I list the commit in every URL, so a reader can open the exact line. The commits:

- Heritrix 3: `internetarchive/heritrix3@e3f9b11` (pom says `3.18.1-SNAPSHOT`)
- BUbiNG: `LAW-Unimi/BUbiNG@50769f8` (last commit 2021-11-04; `build.properties` says `version=0.9.15`)
- Frontera: `scrapinghub/frontera@c94beae` (2025-06-06), plus tag `v0.7.1` for the removed revisiting backend
- Scrapy: `scrapy/scrapy@cb2f58b` (`VERSION` = 2.19.0); scrapy-redis `rmax/scrapy-redis@b4f333a`
- Common Crawl: `commoncrawl/nutch@3270a76` (branch `cc`), `commoncrawl/cc-webgraph@07270e9`
- ManifoldCF: `apache/manifoldcf@465b489` (pom `2.32-SNAPSHOT`)

"Lower number = higher priority" holds in Heritrix, ManifoldCF and HCF. "Higher = first" holds in Scrapy and in Frontera's score. Keep that in mind when you read across sections.

## Heritrix 3: BdbFrontier/WorkQueueFrontier, precedence, cost, budgets, politeness, sheets, revisit

### Takeaway
Heritrix orders work at two levels. Inside a per-host queue, URIs sort by a small integer *precedence* (from a `UriPrecedencePolicy`, cost by default). Across queues, a *queue precedence* picks which inactive queue to activate next, and a session budget (default 3000 cost units) rotates active queues round-robin. Operators tune all of it through Sheets, which are bean-property overrides attached by SURT prefix or by DecideRule. Heritrix has no adaptive recrawl scheduler. Revisits are either a whole new crawl that loads history (dedup/304 revisit records), or a fixed `rescheduleDelaySeconds` per URI, which a sheet can override per site.

### Cited Findings

- Other queue assignment policies in `engine/.../frontier/`: `HostnameQueueAssignmentPolicy`, `IPQueueAssignmentPolicy`, `BucketQueueAssignmentPolicy`, `AssignmentLevelSurtQueueAssignmentPolicy`, `SurtAuthorityQueueAssignmentPolicyWithLimits`, `HostnameQueueAssignmentPolicyWithLimits`, `URIAuthorityBasedQueueAssignmentPolicy`. `ZeroCostAssignmentPolicy` also exists — [frontier package](https://github.com/internetarchive/heritrix3/tree/e3f9b11/engine/src/main/java/org/archive/crawler/frontier)

**WorkQueueFrontier design**
- The class Javadoc reads "Uses in-memory map of all known 'queues' inside a single database. Round-robins between all queues." The fields are `allQueues`; `readyClassQueues` (a `BlockingQueue<String>` of queue keys whose head may be handed out); `inProcessQueues`; `snoozedClassQueues` (a `DelayQueue<DelayedWorkQueue>`) with on-disk `snoozedOverflow` past `MAX_SNOOZED_IN_MEMORY=10000`; `futureUris`, a `StoredSortedMap<Long,CrawlURI>` described as "URIs scheduled to be re-enqueued at future date"; and an inactive map, `getInactiveQueuesByPrecedence()`, keyed by precedence — [WorkQueueFrontier.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/WorkQueueFrontier.java)
- `findEligibleURI()` runs in this order: `wakeQueues()`, `checkFutures()`, `readyClassQueues.poll()`. If no ready queue exists, and `highestPrecedenceWaiting < getPrecedenceFloor()`, it calls `activateInactiveQueue()`. When a queue becomes ready it applies `sheetOverlaysManager.applyOverlaysTo(readyQUri)`, loads overrides, and sets `readyQ.setSessionBudget(getBalanceReplenishAmount())` and `readyQ.setTotalBudget(getQueueTotalBudget())`. So budgets are resolved per queue through sheets, using the queue's head URI. An over-session-budget queue gets `deactivateQueue`. An over-total-budget queue gets `retireQueue` — [WorkQueueFrontier.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/WorkQueueFrontier.java)
- `handleQueue(wq, forceRetire, now, delay_ms)` retires the queue on force-retire. A positive politeness delay snoozes it. Otherwise it calls `getQueuePrecedencePolicy().queueReevaluate(wq)` and then `reenqueueQueue(wq)`. `reenqueueQueue` deactivates the queue instead of making it ready when `highestPrecedenceWaiting < wq.getPrecedence() || wq.getPrecedence() >= getPrecedenceFloor()`, so a better-precedence inactive queue preempts it — [WorkQueueFrontier.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/WorkQueueFrontier.java)
- The Javadoc on `precedenceFloor` (default 255) reads "precedence rank at or below which queues are not crawled". The retire path is reversible. Code comments describe "unretire all queues to 'inactive'. If they still qualify" (for example after a budget is raised) — [WorkQueueFrontier.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/WorkQueueFrontier.java)
- Snoozing: "When a snooze target for a queue is longer than this amount [`snoozeLongMs`, 5 min], the queue will be 'long snoozed' … may be swapped to disk" — [WorkQueueFrontier.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/WorkQueueFrontier.java)

**Budget arithmetic (`WorkQueue`)**
- `isOverSessionBudget()` = `sessionBudget > 0 && (totalExpenditure - expenditureAtLastActivation) > sessionBudget`. `getSessionBalance()` = `sessionBudget - (totalExpenditure - expenditureAtLastActivation)`. `noteError(penalty)` adds the penalty to `totalExpenditure` and increments `errorCount`. The queue report shows `precedence`, `sessionBalance`, `lastCost` and `averageCost = totalExpenditure/costCount` — [WorkQueue.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/WorkQueue.java)
- `balanceReplenishAmount` Javadoc: "amount to replenish budget on each activation (duty cycle)". `errorPenaltyAmount`: "budget penalty for an error fetch". `queueTotalBudget`: "total expenditure to allow a queue before 'retiring' it" — [WorkQueueFrontier.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/WorkQueueFrontier.java)

**Within-queue ordering (BDB key)**
- `BdbMultipleWorkQueues.calculateInsertKey(CrawlURI)` builds the key from the classKey bytes, then a `0` byte, then the URI precedence (clipped to 127, with the warning "URI precedence … exceeds maximum 127 and will be clipped"), then `ordinalPlus = (schedulingDirective << 56) | (ordinal & 0x0000FFFFFFFFFFFF)`. Order inside a queue is therefore precedence, then scheduling directive, then FIFO ordinal — [BdbMultipleWorkQueues.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/BdbMultipleWorkQueues.java)
- Scheduling directives (`SchedulingConstants`): `HIGHEST=0`, `HIGH=1`, `MEDIUM=2`, `NORMAL=3` ("Whenever/end of queue") — [SchedulingConstants.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/modules/src/main/java/org/archive/modules/SchedulingConstants.java)

**Queue precedence policies (`frontier/precedence/`)**
- `BaseQueuePrecedencePolicy` gives every queue `basePrecedence`, default 3, "which leaves room for a simple overlay to prioritize queues". The value "may vary for some queues (as in override settings sheets) or be changed by an operator mid-crawl" — [BaseQueuePrecedencePolicy.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/precedence/BaseQueuePrecedencePolicy.java)
- `HighestUriQueuePrecedencePolicy`: queue precedence = `basePrecedence` + the best (lowest-number) URI precedence currently enqueued. It keeps a `Histotable` of enqueued counts per URI precedence, updated on SCHEDULED/SUCCEEDED/DISREGARDED/FAILED — [HighestUriQueuePrecedencePolicy.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/precedence/HighestUriQueuePrecedencePolicy.java)
- `SuccessCountsQueuePrecedencePolicy` has `incrementCounts` default `"100,1000"`. Per the Javadoc: "with a 'base-precedence' value of 2 … the queue will have a precedence of 2 until 100 URIs are successfully fetched, then a precedence of 3 for the next 1000 … then continue to drop one precedence rank for each 1000". This is a built-in diminishing-returns rule per site — [SuccessCountsQueuePrecedencePolicy.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/precedence/SuccessCountsQueuePrecedencePolicy.java)

**URI precedence policies**
- `CostUriPrecedencePolicy` (the default) sets `curi.setPrecedence(curi.getHolderCost())`. It "simulates the in-queue sorting order in Heritrix 1.x" — [CostUriPrecedencePolicy.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/precedence/CostUriPrecedencePolicy.java)
- `BaseUriPrecedencePolicy` sets a constant `basePrecedence` (default 1), overridable per URI through sheets. `HopsUriPrecedencePolicy` = base + `linkHopCount` (`navlinksOnly=true`) or + full `pathFromSeed` length — [BaseUriPrecedencePolicy.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/precedence/BaseUriPrecedencePolicy.java), [HopsUriPrecedencePolicy.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/precedence/HopsUriPrecedencePolicy.java)
- `PreloadedUriPrecedencePolicy` reads `A_PRECALC_PRECEDENCE` from the uri-history BDB (`PersistProcessor.URI_HISTORY_DBNAME`) and adds it to base. If no value is stored it falls back to `defaultUriPrecedencePolicy`. The offline loader `PrecedenceLoader.main(source, bdbEnvDir)` imports lines of `URI <whitespace> precedence`. This is the hook for externally computed ranks such as PageRank — [PreloadedUriPrecedencePolicy.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/precedence/PreloadedUriPrecedencePolicy.java), [PrecedenceLoader.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/precedence/PrecedenceLoader.java)

**Cost assignment**
- `UnitCostAssignmentPolicy.costOf` = 1 — [UnitCostAssignmentPolicy.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/UnitCostAssignmentPolicy.java)
- `WagCostAssignmentPolicy` ("some wild guesses"): cost starts at 1, +1 if the URI has a query string, and +1 more if the via URI starts with the same non-query prefix. The TODOs list more penalties (many params, path depth, hops) — [WagCostAssignmentPolicy.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/WagCostAssignmentPolicy.java)
- `AntiCalendarCostAssignmentPolicy` = unit cost +1 if the URI matches `CALENDARISH = "(?i)(calendar)|(year)|(month)|(day)|(date)|(viewcal)|(\D19\d\d\D)|(\D20\d\d\D)|(event)|(yr=)|(calendrier)|(jour)"`. Its Javadoc: "Will catch some 'innocent' URIs, but only when uncaught large-volume chaff is ranked higher than caught 'wheat' will this cause notable problems" — [AntiCalendarCostAssignmentPolicy.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/AntiCalendarCostAssignmentPolicy.java)

**Politeness (`DispositionProcessor`)**
- Defaults: `delayFactor=5.0`, `minDelayMs=3000`, `maxDelayMs=30000`, `respectCrawlDelayUpToSeconds=300`, `maxPerHostBandwidthUsageKbSec=0`, `forceRetire=false` — [DispositionProcessor.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/postprocessor/DispositionProcessor.java)
- `politenessDelayFor(curi)` computes `wait = clamp(delayFactor × (fetchCompleted − fetchBegan), minDelayMs, maxDelayMs)`. If `wait < respectCrawlDelayUpToSeconds×1000`, robots.txt `Crawl-delay` for the UA can extend it. The bandwidth cap sets `earliestNextURIEmitTime` from `processedBytes / maxBandwidth` — [DispositionProcessor.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/postprocessor/DispositionProcessor.java)

**Sheets and overlays (the operator tuning mechanism)**
- A `Sheet` is a "Collection of overrides: alternative values for object properties that should apply in some contexts". Its `map` goes from a full bean property path (for example `frontier.balanceReplenishAmount` or `queuePrecedencePolicy.basePrecedence`) to a value. It is "primed" against the bean factory to type-check — [Sheet.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/commons/src/main/java/org/archive/spring/Sheet.java)
- Associations come in two kinds. `SurtPrefixesSheetAssociation` has `surtPrefixes` plus `targetSheetNames`. `DecideRuledSheetAssociation` has `rules` (a DecideRule; sheets apply "If the final ruling is ACCEPT") and `order` (an `Ordered` int; ties broken by bean name). `SheetOverlaysManager` keeps `sheetNamesBySurt` (a `NavigableMap`) and a sorted `ruleAssociations` set. Sheets "may be added by other means (mid-crawl reconfiguration)" — [SheetOverlaysManager.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/spring/SheetOverlaysManager.java), [DecideRuledSheetAssociation.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/spring/DecideRuledSheetAssociation.java), [SurtPrefixesSheetAssociation.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/spring/SurtPrefixesSheetAssociation.java)

**Revisit, dedup and rescheduling**
- `ReschedulingProcessor.rescheduleDelaySeconds` defaults to `-1` ("don't reschedule"). When positive, it sets `curi.setRescheduleTime(now + 1000×rds)`. Prerequisites are never rescheduled. Its Javadoc: "use a local setting (perhaps overlaid to vary based on the URI) to set an exact future reschedule time". The frontier puts such URIs into `futureUris`, and `checkFutures()` re-enqueues them when due — [ReschedulingProcessor.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/postprocessor/ReschedulingProcessor.java), [WorkQueueFrontier.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/WorkQueueFrontier.java)
- `FetchHistoryProcessor.historyLength=2` stores status, fetch-began time, content digest, `ETag`, `Last-Modified` and reference length per fetch. On HTTP 304 it copies the previous digest forward, annotates `duplicate:server-not-modified`, and sets a `ServerNotModifiedRevisit` profile, which the WARC writer emits as a revisit record — [FetchHistoryProcessor.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/modules/src/main/java/org/archive/modules/recrawl/FetchHistoryProcessor.java)
- `ContentDigestHistoryLoader` creates an `IdenticalPayloadDigestRevisit` when the digest was seen before, recording the original URL, date and WARC record id, with annotation `duplicate:digest` — [ContentDigestHistoryLoader.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/modules/src/main/java/org/archive/modules/recrawl/ContentDigestHistoryLoader.java)
- `PersistLoadProcessor.preloadSource` / `preloadSourceUrl` copies prior-crawl history (a log or BDB) into the current store at startup "for consultation by a later recrawl" — [PersistLoadProcessor.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/modules/src/main/java/org/archive/modules/recrawl/PersistLoadProcessor.java)

### Inferences
- Effective global order is lexicographic: (queue precedence, round-robin among queues of equal precedence via session budgets) for picking the queue, then (URI precedence, directive, FIFO) inside the queue. Under `UnitCost` and the 3000 default, one active queue can emit about 3000 URIs before the queues behind it get a turn. A lower `balanceReplenishAmount` gives finer interleaving at the cost of more queue churn.
- Deprioritisation in Heritrix is "raise the precedence number". Exclusion without deletion is "set precedence ≥ `precedenceFloor`": the queue stays, is reported, and is never crawled. A UI "pause this source" maps onto that.
- For a Telegram directory, `SuccessCountsQueuePrecedencePolicy` is a ready-made model for diminishing returns per *referrer cluster*: precedence worsens after N successes. `PreloadedUriPrecedencePolicy` is the model for injecting an offline graph rank such as harmonic centrality over the mention graph as an additive precedence.
- Heritrix's `ReschedulingProcessor` with per-SURT sheets amounts to "per-segment fixed revisit interval". It has no change-rate adaptivity. Heritrix users who need adaptivity run successive crawls with dedup (the IA practice) rather than in-crawl adaptive refresh.

### Gaps
- I did not read the `activateInactiveQueue()` body in full, so how it picks among multiple queues at the same precedence (FIFO in `inactiveQueuesByPrecedence.get(p)`) is inferred from the map's type (`Queue<String>`).
- I found no Heritrix primary source giving production lessons on budget values. The wiki pages ("Frontier precedence", "Sheets") were not fetched within the tool budget.
- `parallelQueues` semantics in `SurtAuthorityQueueAssignmentPolicy` (splitting one host across N queues) were not verified in code.

## BUbiNG: workbench, visit states, politeness, sieve, next-host selection, scale

### Takeaway
BUbiNG is a fully distributed, archival, *breadth-first-per-host* crawler with no refresh. Ordering is entirely politeness-driven. A `Workbench` is a `DelayQueue` of per-IP `WorkbenchEntry`s, each a priority queue of per-host `VisitState`s ordered by `nextFetch`, each holding a FIFO of path+query. Dedup is a disk-based `MercatorSieve` behind an approximate LRU URL cache that drops more than 90% of discovered URLs. One agent reaches about 10,000 pages/s on a 64-core box in vitro.

### Cited Findings
- URL states are *unknown*, *waiting* (in the sieve), *ready* (out of the sieve into the `readyURLs` `ByteArrayDiskQueue`) and *visited*. The sieve guarantees each URL is emitted once. `enqueue()` checks, in order: the per-scheme+authority cap, the URL cache, which agent owns the URL (forwarded via JAI4J), then the sieve — [Frontier.java](https://github.com/LAW-Unimi/BUbiNG/blob/50769f8/src/it/unimi/di/law/bubing/frontier/Frontier.java)
- `VisitState` is the per-scheme+authority state. It holds `nextFetch`, a queue of path+queries, cached robots filter and cookies. `nextFetch == Long.MAX_VALUE` means the host hit its URL cap. Errors back off: start at `ParsingThread#EXCEPTION_TO_WAIT_TIME`, "doubled every time" up to `EXCEPTION_TO_MAX_RETRIES`, then either drop the URL or, for host-killer exceptions, `schedulePurge()` sets the count to `Integer.MAX_VALUE` and discards the host's URLs — [VisitState.java](https://github.com/LAW-Unimi/BUbiNG/blob/50769f8/src/it/unimi/di/law/bubing/frontier/VisitState.java)
- `WorkbenchEntry` is the per-IP entry (64-bit IP hash). It holds a `PriorityQueue<VisitState>` ordered by `VisitState.nextFetch`, and its own delay is `max(entry.nextFetch, top.nextFetch)`. "We can just take a WorkbenchEntry … with the guarantee that it is ready to be visited" — [WorkbenchEntry.java](https://github.com/LAW-Unimi/BUbiNG/blob/50769f8/src/it/unimi/di/law/bubing/frontier/WorkbenchEntry.java)
- `Workbench`: acquiring a VisitState removes its WorkbenchEntry from the workbench, "so it is not possible to acquire any other VisitState with the same IP address … we never download data using two different FetchingThread instances from the same IP" — [Workbench.java](https://github.com/LAW-Unimi/BUbiNG/blob/50769f8/src/it/unimi/di/law/bubing/frontier/Workbench.java)
- `Distributor` refills the workbench from `readyURLs`, or from the `WorkbenchVirtualizer` (on-disk per-host queues), only while the workbench is not full *and* the "front" (number of IPs ready) is below the required size. An idle distributor sleeps with exponential backoff — [Distributor.java](https://github.com/LAW-Unimi/BUbiNG/blob/50769f8/src/it/unimi/di/law/bubing/frontier/Distributor.java)
- Config (`StartupConfiguration`): `schemeAuthorityDelay` ("minimum delay between two consecutive fetches from the same scheme+authority"), `ipDelay`, `ipDelayFactor` (default 0; the IP delay is multiplied by `ipDelayFactor · k/(k+1) · knownCount` for multi-agent IP sharing, "BUbiNG will wait at least ipDelay"), `keepAliveTime` (default 0), `maxUrlsPerSchemeAuthority`, `maxUrls`, `workbenchMaxByteSize`, `sieveSize`. The test properties use `schemeAuthorityDelay=4000`, `ipDelay=500`, `maxUrlsPerSchemeAuthority=100`, `fetchingThreads=100`, `parsingThreads=64`, `dnsThreads=10`, `workbenchMaxByteSize=128Mi`, `sieveSize=256Mi`, `urlCacheMaxByteSize=2G`, `robotsExpiration=1d` — [StartupConfiguration.java](https://github.com/LAW-Unimi/BUbiNG/blob/50769f8/src/it/unimi/di/law/bubing/StartupConfiguration.java), [bubing-test.properties](https://github.com/LAW-Unimi/BUbiNG/blob/50769f8/data/it/unimi/di/law/bubing/util/bubing-test.properties)
- `MercatorSieve` stores each known key as a 64-bit hash on disk. New hashes are buffered in memory with the keys in an auxiliary file. When the buffer fills, it is sorted, merged against the known set, and unseen keys are emitted in first-appearance order, using only sequential I/O — [MercatorSieve.java](https://github.com/LAW-Unimi/BUbiNG/blob/50769f8/src/it/unimi/di/law/bubing/sieve/MercatorSieve.java)
- Paper (arXiv 1601.06919 / TWEB 2018): the visit is "an exact breadth-first visit" per host. The workbench is "a priority queue of priority queues of FIFO queues". The URL cache discards "more than 90% of the URLs discovered". The authors say DRUM loses BFS order and Bloom filters lack guarantees. BUbiNG "does not perform any refresh of the visited pages". Near-duplicates are caught by digesting normalised HTML into a Bloom filter. The authors "always set the host politeness delay equal to the IP politeness delay" in experiments. A non-BFS priority "is easy to add if it is per host and per agent" — [BUbiNG paper (ar5iv)](https://ar5iv.labs.arxiv.org/html/1601.06919)
- Throughput: a 64-core/64 GB workstation does more than 10,000 pages/s and more than 160 MB/s. In vitro, 4 agents averaged 40,600 pages/s (about 10,150 per agent, 1,000 fetching threads). In a no-I/O test on 40 cores: 16,000 pages/s average, 22,500 peak. Heritrix on the same hardware did 370 pages/s (10 s politeness, 1,000 threads). Nutch/ClueWeb09 did about 7.55 pages/s per machine on 100 machines. In vivo, one agent sustained 1.2 Gb/s on a 2 Gb/s link — [BUbiNG paper (ar5iv)](https://ar5iv.labs.arxiv.org/html/1601.06919)
- Lessons the paper states: blocking I/O with thousands of threads beat async I/O; Berkeley DB was "a serious bottleneck" (replaced by a memory-mapped virtualizer); Hadoop batch distribution is "easy, but not efficient"; skewed per-host/IP delays can make todo-queue order diverge from true priority — [BUbiNG paper (ar5iv)](https://ar5iv.labs.arxiv.org/html/1601.06919)

### Inferences
- BUbiNG answers "what next" with "whichever polite slot frees first, BFS within host". It has no value-based priority. Its relevant lesson for a Telegram directory is the two-level politeness key: host plus IP, which maps to channel plus proxy/IP. It also gives a cheap dedup front (cache, then sieve) for the roughly 1M mined handles.
- The URL-cache result (more than 90% of discoveries are repeats) suggests that mining references from posts will mostly rediscover known handles. An in-memory LRU of handle fingerprints in front of the DB upsert would remove most write load.

### Gaps
- I did not verify per-agent defaults in a shipped production properties file (only the test one). The paper gives no default delay values.

## Frontera, Scrapy, scrapy-redis and HCF: strategies, scores, queues, revisits

### Takeaway
Frontera separates *strategy* (assign a 0..1 score per request) from *backend queue* (store and dequeue, partitioned by host). The HBase queue turns the score into lexicographic row keys (`1 − score` at 0.01 and 0.001 resolution) and dequeues in batches with per-host caps. Revisiting was a separate SQLAlchemy backend with a fixed interval (default 1 day). It is gone from master. Scrapy itself has an integer `Request.priority` (higher first) adjusted by depth, redirect and retry, and a default scheduler queue that is downloader-slot aware.

### Cited Findings

### Inferences
- Possible inconsistency, worth checking before copying code. On master, `MemoryQueue` uses a `heapq` min-heap comparing `meta['_scr']`, and the SQLAlchemy `Queue._order_by` default is `ORDER BY score, created_at` ascending. Read literally, both pop *lowest* score first, while HBase explicitly inverts (`1 − score`) to pop highest first. I found no compensating negation elsewhere in `contrib/`, `core/` or `worker/` ([memory/__init__.py](https://github.com/scrapinghub/frontera/blob/c94beae/frontera/contrib/backends/memory/__init__.py), [sqlalchemy/components.py](https://github.com/scrapinghub/frontera/blob/c94beae/frontera/contrib/backends/sqlalchemy/components.py)). Only the HBase backend clearly implements "higher score first".
- `justify_request_score_by_hostname` is a cheap fairness trick: random host bands keep one high-scoring domain from monopolising the head of a single ordered queue. The same hash-band trick would interleave sources in a Postgres `ORDER BY score` frontier.
- Frontera's widening scan (limit ×5.5, at least N hosts, at most M per host) works as a "diverse batch" dequeue on top of a single sorted index. It maps directly to a SQL `ORDER BY priority LIMIT k` followed by a per-key cap.

### Gaps
- I did not find a primary document describing Zyte's internal HCF priority implementation beyond the API (`p` lower first). Production lessons from Scrapinghub's HBase-backed broad crawls are not in the fetched sources.

## Common Crawl: monthly selection, harmonic centrality, per-domain budgets, revisits

### Takeaway
Since 2017 Common Crawl steers a batch Nutch crawl with domain-level harmonic centrality (HC) ranks computed from host and domain web graphs built over 3 monthly crawls. A domain's HC rank sets its "budget": URLs sampled or fetched, URLs per host, and subdomains. Budgets are log-interpolated from 35M URLs / 150k per host / 500k subdomains at the top to 1k / 800 / 6 for the long tail. Each crawl re-injects links sampled from the previous crawl, a shallow priority-first "fresh" crawl, sitemaps and homepages, and updates the CrawlDb status without link additions.

### Cited Findings
- Three phases of seeds and prioritisation: 2008–2012 in-house PageRank; 2013–2016 Nutch with the blekko seed donation (blekko "donates ranking and metadata of 140 million web sites and 22 billion pages"); 2017–now Nutch with harmonic centrality. Occasional 2016–2018 donations of "up to 400 million URLs" were "not enough to 'feed' the crawler" — [Nagel, "Common Crawl: Data Collection and Use Cases for NLP", Feb 2023](https://markup.co.uk/hg/cc/work/raw-file/tip/nagel.230206.pdf)
- 2017–now workflow: step 4 is "update CrawlDb with status from preceding crawl (no link additions)", then "flag dups in CrawlDb (by signature and redirect target)". Injection draws on "links sampled from preceding crawl (≈4 billion)"; "'fresh' links from shallow, priority-first crawl (≈1.5 billion)" seeded with homepages of 40 million host/domain names, run as 9 cycles in one day; and "URLs sampled from 20 million sitemaps (≈4 billion)" — [Nagel 2023](https://markup.co.uk/hg/cc/work/raw-file/tip/nagel.230206.pdf)
- Why prioritise: a monthly crawl has "3 billion page captures with 500+ billion links, 25+ billion unique URLs linked"; "a single sitemap … may list up to 2.5 billion URLs" — [Nagel 2023](https://markup.co.uk/hg/cc/work/raw-file/tip/nagel.230206.pdf)
- Domain HC ranks are used "to define a 'budget' for every domain how many URLs/pages are sampled or fetched", "to sample sitemaps or home pages for URL discovery (always for top-ranking domains, sometimes for lower ranks)", and "as domain-level scores 'projected' to the page-level by OPIC or inlink counts". Per-domain limits (2022): "top domains: 35 million URLs, 150k URLs per host, 500k subdomains"; "long tail (below rank 64M or yet unseen): 1k URLs, 800 per host, 6 subdomains"; "log distribution between top and tail" — [Nagel 2023](https://markup.co.uk/hg/cc/work/raw-file/tip/nagel.230206.pdf)
- The web graphs are built "based on 3 monthly crawls" and "used to 'steer' the crawler for the next three crawls". HC is "more robust against link spam than page rank" — [Nagel 2023](https://markup.co.uk/hg/cc/work/raw-file/tip/nagel.230206.pdf); [CC hostgraph 2017 post](https://commoncrawl.org/blog/hostgraph-2017-feb-mar-apr-crawls)
- February 2019 crawl post: limits "are now configurable and are based on the harmonic centrality rank of a domain". There is a new cap on hosts per domain, "from 500,000 subdomains for top-ranking domains" to "less than 100 for low-ranking domains". "New URLs are sampled based on the host and domain ranks (harmonic centrality)". Seeds included sitemaps and RSS/Atom feeds, a breadth-first side crawl of at most 5 links from the homepages of the top 50M hosts and domains, and outlinks sampled from the previous crawl's WAT files. 2.9B pages, of which 750M were URLs never in any archive before — [CC Feb 2019 crawl announcement](https://blog.commoncrawl.org/blog/february-2019-crawl-archive-now-available)
- The ranks are computed in `cc-webgraph` by running WebGraph `HyperBall --offline --log2m $HYPERBALL_REGISTERS --harmonic-centrality` and `PageRankParallelGaussSeidel`. The joined ranks file header is `#harmonicc_pos #harmonicc_val #pr_pos #pr_val #host_rev`. The register count is "empirically determined" per machine and graph size — [process_webgraph.sh](https://github.com/commoncrawl/cc-webgraph/blob/07270e9/src/script/webgraph_ranking/process_webgraph.sh), [webgraph_config.sh](https://github.com/commoncrawl/cc-webgraph/blob/07270e9/src/script/webgraph_ranking/webgraph_config.sh)
- Harmonic centrality definition (linked from the cc-webgraph README): H(x) = Σ_{y≠x} 1/d(y,x), with 1/∞ = 0, so it handles disconnected graphs — [cc-webgraph README](https://github.com/commoncrawl/cc-webgraph/blob/07270e9/README.md) → [Wikipedia: Harmonic centrality](https://en.wikipedia.org/wiki/Centrality#Harmonic_centrality)
- CC's Nutch fork adds `Generator2`: group by host or domain with a secondary sort by score descending; per-domain limits (`generate.domain.limits.file`, `generate.max.hosts.per.domain`, `generate.max.count.per.host.by.domain`); and `generate.count.keep.min.urls.per.segment` to keep same-host URLs together and cut DNS and robots.txt overhead. It builds about 100 segments in one job. The limits file is tab-separated: `domain`, `max URLs per domain and segment`, `max URLs per host and segment`, `max hosts per domain over all segments`, `max partitions (fetcher tasks)` (example `wikipedia.org 5000 500 20 1`) — [Generator2.java](https://github.com/commoncrawl/nutch/blob/3270a76/src/java/org/apache/nutch/crawl/Generator2.java), [generate-domain-limits.txt.template](https://github.com/commoncrawl/nutch/blob/3270a76/conf/generate-domain-limits.txt.template), [CC nutch README](https://github.com/commoncrawl/nutch/blob/3270a76/README.md)
- Nutch defaults shipped in the fork's `nutch-default.xml`: `generate.max.count=-1`, `generate.count.mode=host`, `generate.min.score=0`, `crawl.gen.delay` default 7 days (from `Generator2`), `db.fetch.interval.default=2592000` (30 d), `db.fetch.interval.max=7776000` (90 d), `db.fetch.schedule.class=DefaultFetchSchedule`, and adaptive schedule params `inc_rate=0.4`, `dec_rate=0.2`, `min_interval=60`, `max_interval=31536000`, `sync_delta=true`, `sync_delta_rate=0.3`, `fetcher.server.delay=5.0`, `fetcher.threads.per.queue=1`, `fetcher.queue.mode=byHost` — [nutch-default.xml](https://github.com/commoncrawl/nutch/blob/3270a76/conf/nutch-default.xml)
- Politeness and operations: "min. 5 seconds between successive requests to the same host", "further slow down (exponential backoff) if host responds with errors", "no (residential) proxies". Fetch list layout: 100 segments processed sequentially over 14 days, 40 partitions each, partitioned by host, every partition shuffled. 4B URLs from 45M domains and 60M hosts on the fetch list; 3B fetched from 35M domains and 45M hosts. Fetching runs on 20 nodes (2 cores, 32 GB). The CrawlDb holds 25B URLs (1.6 TiB, about $40/month on S3) — [Nagel 2023](https://markup.co.uk/hg/cc/work/raw-file/tip/nagel.230206.pdf)
- Spam lesson: in October 2017 a spam cluster took 56M pages (1.5% of the crawl) from 70,000 domains, with 320,000 domains and 2.5B subdomains known from links. Each subdomain costs a DNS lookup and a robots.txt fetch. The fixes were a cap on subdomains per domain and blocking clusters with a heuristic: "low-ranking domains with too many outlinks or subdomains are suspicious", sorted by log2(HC rank × number of subdomains). Top offenders score about 44–45; blogspot.com scores 26.89 — [Nagel 2023](https://markup.co.uk/hg/cc/work/raw-file/tip/nagel.230206.pdf)

### Inferences
- The CC budget rule amounts to a per-domain cap that is log-linear between two anchors. One plausible reading is log B(r) = log B_top + (log B_tail − log B_top) · f(r), with f increasing from 0 at the top rank to 1 at rank 64M (f may be linear in r or in log r; unstated). For a Telegram directory, "domain" ≈ channel and "subdomains" ≈ distinct handles a source introduces. The spam heuristic (low rank × many introduced handles) transfers directly to bot or spam channels that mention thousands of handles.
- CC's revisit behaviour is implicit. Previously fetched URLs come back only if sampled again, and the CrawlDb carries status and signature, not a refresh schedule. For refresh, the Nutch `AdaptiveFetchSchedule` constants (×(1−0.2) when changed, ×(1+0.4) when unchanged, clamped to [60 s, 1 yr]) are the closest primary-source formula in this lineage. The cc fork's actual config values are not public in what I read.

### Gaps
- The exact interpolation formula between the top and tail budgets, and whether it runs over rank or log-rank, is not published in the sources I found.
- I did not find CC's production `nutch-site.xml` (fetch-schedule class, `generate.max.count`, OPIC settings). The values above are upstream defaults as shipped in the fork.
- The "crawl-history"/URL-database specifics (how many previously-fetched URLs are revisited per crawl) are not given beyond "links sampled from preceding crawl (≈4 billion)".

## Apache ManifoldCF: continuous crawling schedule and bin-based document priority

### Takeaway
ManifoldCF fixes a document's priority at enqueue time with a per-"bin" counter (bin = throttle key such as hostname). The k-th document queued into a bin gets priority ln(1 + k · (1 + 1/(50 ms · maxRate))). Workers pull `ORDER BY docpriority ASC`, so documents interleave round-robin across bins, and slower-throttled bins are pushed back in proportion. Continuous jobs reschedule each document at `now + min(recrawlInterval + timeAmt, maxInterval)`, bounded by connector-provided lower and upper bounds, and expire it at `origination + expiration`, whichever comes first.

### Cited Findings
- `PriorityCalculator` constant: `minMsPerFetch = 50.0` ("originally based on 100 documents/second, but adjusted downward"). Per bin, `binCountScaleFactor = 1 + 1/(minMsPerFetch × maxFetchRate)` (∞ if the rate is 0), and `weightedMinimumDepth = currentMinimumDepth / binCountScaleFactor` — [PriorityCalculator.java](https://github.com/apache/manifoldcf/blob/465b489/framework/pull-agent/src/main/java/org/apache/manifoldcf/crawler/system/PriorityCalculator.java)
- `getDocumentPriority()`: for each of the document's bins, `thisCount = rt.getIncrementBinValue(connectorClass, binName, weightedMinimumDepth)`, `adjusted = thisCount × scale`, `highest = max(adjusted)`, `priority = ln(1 + highest)`. The Javadoc: "Priorities are reversed, and in log space, so that zero (0.0) is considered the highest possible priority". The slowest throttle wins. The comments derive the design: priority −log(1/(1+B)) for the B-th unthrottled member, with `k = B · (1 + 1/(T·F))` for throttled bins — [PriorityCalculator.java](https://github.com/apache/manifoldcf/blob/465b489/framework/pull-agent/src/main/java/org/apache/manifoldcf/crawler/system/PriorityCalculator.java)
- Throttle limits come from the repository connection's throttle specs (regex → rate). If several match, "the most conservative fetch rate is chosen" — [PriorityCalculator.java](https://github.com/apache/manifoldcf/blob/465b489/framework/pull-agent/src/main/java/org/apache/manifoldcf/crawler/system/PriorityCalculator.java); end-user docs: "Each connection type has its own notion of 'throttling bin' … the Web connection type uses a document's server name as the throttling bin" — [end-user-documentation.xml](https://github.com/apache/manifoldcf/blob/465b489/site/src/documentation/content/xdocs/en_US/end-user-documentation.xml)
- `BinManager.getIncrementBinValues(connectorClass, binName, newBinValue, count)` does `SELECT … FOR UPDATE`, sets the start to `max(stored, newBinValue)`, returns consecutive values, and stores start+count. It retries on `DATABASE_TRANSACTION_ABORT` — [BinManager.java](https://github.com/apache/manifoldcf/blob/465b489/framework/pull-agent/src/main/java/org/apache/manifoldcf/crawler/bins/BinManager.java)
- The work query orders by `docpriority ASC`. A code comment records a production lesson: the query "did just fine until adaptive recrawling was seriously tried. Then, because every document in a job was still active, it failed miserably, actually causing Postgresql to stop responding … there just isn't any way to sort 1M documents without working with a monster resultset. I introduced a new index … based solely on docpriority" — [JobManager.java](https://github.com/apache/manifoldcf/blob/465b489/framework/pull-agent/src/main/java/org/apache/manifoldcf/crawler/jobs/JobManager.java)
- Job types: `TYPE_CONTINUOUS = 0` ("Never stops, just reschedules individual documents indefinitely") and `TYPE_SPECIFIED = 1`. The getters are `getInterval()` (rescheduling interval, ms, null = forever), `getMaxInterval()`, `getExpiration()`, `getReseedInterval()`, and `getPriority()` ("a number between 1 and 10") — [IJobDescription.java](https://github.com/apache/manifoldcf/blob/465b489/framework/pull-agent/src/main/java/org/apache/manifoldcf/crawler/interfaces/IJobDescription.java)
- `calculateDocumentRescheduleTime(currentTime, timeAmt, id)`: `actualInterval = recrawlInterval + timeAmt`, capped at `maxInterval`, so `recrawlTime = now + actualInterval`. A connector-supplied lower bound raises it and an upper bound lowers it. The caller's comment: "the formula is to calculate the running avg interval between changes, add an additional interval (which comes from the job description) … we really want to calculate the interval from the last time change was detected, but this is not implemented yet". Expire time = origination time + expiration. The action is RESCAN if recrawl comes before expire, otherwise REMOVE. Aborted documents requeue at time 0 — [WorkerThread.java](https://github.com/apache/manifoldcf/blob/465b489/framework/pull-agent/src/main/java/org/apache/manifoldcf/crawler/system/WorkerThread.java)
- The Scheduling tab exposes: continuous vs scan-once; expiration; "The minimum interval before a document is re-checked"; "The maximum interval before a document is re-checked"; and "How long to wait before reseeding initial documents". Job priority: "The higher the number, the more important it is considered for that job's documents to be fetched first." "Continuous jobs cannot remove no-longer-included documents from the queue" — [end-user-documentation.xml](https://github.com/apache/manifoldcf/blob/465b489/site/src/documentation/content/xdocs/en_US/end-user-documentation.xml)
- Web and RSS connectors split throttling into "Bandwidth" (maximum values, which hold a thread for the wait) and "Throttling" (average rates, which affect how often documents are *scheduled*, "so it does not waste threads") — [end-user-documentation.xml](https://github.com/apache/manifoldcf/blob/465b489/site/src/documentation/content/xdocs/en_US/end-user-documentation.xml)

### Inferences
- The recrawl backoff in this code is *additive with a cap*: interval = base + observed time amount, ≤ max. It is not exponential. The prompt's "exponential backoff on unchanged docs" is not borne out by `calculateDocumentRescheduleTime`. Connectors can still impose bounds.
- The bin counter is a strong fit for a Telegram directory. Use "bin" = discovering source channel, or proxy. Each newly discovered handle takes `ln(1 + next_counter(bin) × scale)`, so one prolific source cannot flood the head of the queue. A single B-tree index on that column gives an O(log n) `ORDER BY … LIMIT` over about 1M rows, which is ManifoldCF's own Postgres lesson.
- The "reset to current minimum depth" (`weightedMinimumDepth`) stops a newly seen bin from jumping ahead of everything already queued. A new bin starts at the queue's current depth, not at 0.

### Gaps
- Where `timeArray` (`timeAmt`) is computed, and how job priority 1–10 combines with `docpriority` in the dequeue query, were not traced in the files I read. ReprioritizationTracker's minimum-depth update rule was not read.

## Operator-facing knobs across the five systems, and what transfers to a Telegram directory crawler

### Takeaway
Each project exposes a different kind of control. Heritrix lets an operator override any property by SURT prefix or DecideRule (Sheets), including precedence, budgets, politeness and revisit delay, and live, mid-crawl. Common Crawl ships a per-domain limits file derived from graph rank. Frontera and HCF push all policy into code (strategy score) with a few global caps. ManifoldCF offers per-bin throttle regexes, job-level priority 1–10 and min/max recrawl intervals. BUbiNG offers only politeness delays and per-host URL caps.

### Cited Findings
- Heritrix: sheets via `SurtPrefixesSheetAssociation(surtPrefixes, targetSheetNames)` and `DecideRuledSheetAssociation(rules, order, targetSheetNames)`, applied at queue activation (`applyOverlaysTo` before reading `balanceReplenishAmount` and `queueTotalBudget`). ### Inferences (adaptation to ~1M handles, ~80k fetches/day shared, ~500k live entries)
- Discovery order. The closest primary-source precedent for "which newly mined handle first" is CC's model: rank by centrality of the reference graph, then cap by rank. HC over a 1M-node mention graph is cheap with HyperBall, and even in-degree from distinct sources is a defensible first cut. ManifoldCF's per-bin log counter (bin = source channel) can supply fairness across sources, and Heritrix's precedence floor can handle "never fetch".
- Revisit order. No system here has a value-aware refresh scheduler. The available formulas are fixed per segment (Heritrix `rescheduleDelaySeconds`, Frontera 1-day interval), additive with a cap (ManifoldCF), and multiplicative with clamps (Nutch Adaptive: ×0.8 on change, ×1.4 unchanged, [60 s, 1 yr]). At 500k live entries and well under 80k/day available for refresh, a uniform cycle is at least about 6–7 days even if refresh took the whole budget. So intervals must differ by entry value, which is what Heritrix sheets and ManifoldCF bounds let an operator express.
- Operator rules. Heritrix's sheet model maps cleanly onto UI rules: predicate (handle pattern, tag, source, language) → ordered override of {precedence delta, budget, revisit interval, floor/exclude}, evaluated in `order` with the last ACCEPT winning. Its lesson is to evaluate rules where the scheduler reads the value (at queue activation), not at insert time, so live edits take effect without rewriting rows. That suits a "boost/deprioritise" UI better than baking scores into stored priorities (Frontera's `SQLALCHEMYBACKEND_REVISIT_INTERVAL` docs note that changes do not affect already-queued items).
- Shared budget with user syncs. Heritrix's per-queue session budget and Frontera's `max_requests_per_host` are the two precedents for keeping one class of work from starving another. A directory crawler can treat "user-facing sync" and "directory crawl" as two queues with separate budgets, in the same shape as Heritrix's precedence plus session budget.
- Proxies. BUbiNG's two-level delay (host plus IP), and its rule that acquiring a slot removes the IP from the workbench, is the reference design for per-proxy politeness where Telegram's per-IP limits are the binding constraint.

### Gaps
- None of these systems documents a combined discovery-plus-refresh budget split (for example "X% new, Y% revisit"). Common Crawl's numbers (≈4B sampled previous-crawl links, ≈1.5B fresh, ≈4B sitemap) are the only published mix, and they are injection counts, not fetch shares.
