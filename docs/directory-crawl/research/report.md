# Price every probe by what it buys

The open-source crawlers studied here are Nutch, StormCrawler/URLFrontier, Heritrix, BUbiNG, Frontera/Scrapy, Common Crawl and ManifoldCF. None of them has a value-aware frontier. Each orders work by one sort key (a float score, an integer precedence or a due date) and adds per-key caps, and the formulas worth adopting come from the academic literature. For newly discovered handles the evidence points one way. Rank by expected yield per probe, P(live, in a wanted language | features), and estimate it from **distinct citers weighted by citer quality and citer language**. Never use raw reference counts, because plain backlink ordering scored **0.50 against random's 0.50** in the largest controlled comparison. For refresh, Telegram has an advantage no web paper had. A t.me/s fetch reveals the *exact* number of new posts, so the posting rate has a closed-form estimate, (prior + posts seen) / (prior + days observed). That rate should feed a concave, non-saturating value so fast channels are not over-served and silent ones are never starved. Proportional allocation scored **0.12 freshness against 0.62 optimal** in Cho and Garcia-Molina's data. The discovery/refresh split has no published optimum, and the survey literature says so. It has to be an explicit, operator-set share with work-conserving overflow, because a strict "new outranks known" rule is exactly how 123k refreshes went overdue. In your own measurements the strongest discovery lever is citer language. Probes of fa/en-cited targets found live fa/en channels at **about 6.5 times** the rate of the rest, against 3.3x for the best-vs-worst reference kind and 1.8x for citer count. The design at the end turns all of this into two scores, one estimator, a capacity rule and an operator rules table modelled on Heritrix sheets.

## Seven production crawlers order work with one sort key and a cap

The open-source systems split into three families. The first sorts by a score. Nutch's Generator drops anything not due, computes one float through a chain of scoring filters (`generatorSortValue`), sorts descending, and walks hosts until `topN` is reached, skipping a host once it holds `generate.max.count` URLs ([Generator.java](https://github.com/apache/nutch/blob/master/src/java/org/apache/nutch/crawl/Generator.java)). Its default OPIC plugin starts a new link at score 0 and sets `score = old + Σ inlink cash` on every update. History never decays, and the parent keeps its own cash while giving it away, which a code comment admits is "contrary to the algorithm descr. in the paper" ([OPICScoringFilter.java](https://github.com/apache/nutch/blob/master/src/plugin/scoring-opic/src/java/org/apache/nutch/scoring/opic/OPICScoringFilter.java)). The Nutch wiki's own verdict is that "you can't recrawl, at least not without having the recrawled pages get inflated scores" ([Fixing OPIC](https://cwiki.apache.org/confluence/spaces/NUTCH/pages/115512062/FixingOpicScoring)). Frontera's discovery strategy has fixed tiers (seeds 0.9, home pages 0.8, "links of interest" 0.7, other links 0.5) and a per-domain cap of 100 pages. It also hashes each host into one of ten bands so a single high-scoring domain cannot monopolise the queue head ([discovery strategy](https://github.com/scrapinghub/frontera/blob/c94beae/frontera/strategy/discovery/__init__.py)). Scrapy has an integer `Request.priority` adjusted by depth, redirect and retry ([default_settings.py](https://github.com/scrapy/scrapy/blob/cb2f58b/scrapy/settings/default_settings.py)).

The second family sorts by time. StormCrawler has no score at all. A scheduler maps `(status, metadata)` to `nextFetchDate`, and every DISCOVERED URL gets `now`, so new URLs compete with overdue refreshes on arrival time alone ([DefaultScheduler.java](https://github.com/apache/stormcrawler/blob/main/core/src/main/java/org/apache/stormcrawler/persistence/DefaultScheduler.java)). URLFrontier has no priority field either. Within a queue, URLs are served by scheduling date, so StormCrawler issue #2185 describes the result as rotating between per-host queues served FIFO, where "the depth of a URL plays no role" ([issue #2185](https://github.com/apache/stormcrawler/issues/2185)). BUbiNG is an exact per-host breadth-first crawler that "does not perform any refresh of the visited pages". Its one transferable lesson is that its URL cache discards **more than 90%** of discovered URLs as repeats ([BUbiNG paper](https://ar5iv.labs.arxiv.org/html/1601.06919)).

The third family uses ranks and budgets, and it is where the operator ideas live. Heritrix sorts inside a per-host queue by a small integer precedence (cost by default) and picks queues by a queue precedence. A session budget of 3000 cost units rotates active queues, and any queue at or past `precedenceFloor` (255) is kept but never crawled ([WorkQueueFrontier.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/WorkQueueFrontier.java)). Operators override any bean property through **Sheets**, attached by SURT prefix or by a DecideRule with an explicit order, and the overrides apply live at queue activation ([SheetOverlaysManager.java](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/spring/SheetOverlaysManager.java)). `SuccessCountsQueuePrecedencePolicy` builds diminishing returns into a site's priority: precedence worsens after 100 successes, then by one rank per further 1000 ([source](https://github.com/internetarchive/heritrix3/blob/e3f9b11/engine/src/main/java/org/archive/crawler/frontier/precedence/SuccessCountsQueuePrecedencePolicy.java)). Common Crawl computes domain harmonic centrality over three monthly crawls and turns rank into a budget that is log-interpolated from **35M URLs, 150k per host and 500k subdomains** at the top down to **1k, 800 and 6** for the long tail. It chose harmonic centrality because it is "more robust against link spam than page rank" ([Nagel 2023](https://markup.co.uk/hg/cc/work/raw-file/tip/nagel.230206.pdf)). ManifoldCF gives the k-th document queued into a throttle bin the priority `ln(1 + k·(1 + 1/(50ms · maxRate)))` and dequeues ascending, which interleaves bins round-robin. Its code also records a Postgres lesson: sorting a million active documents without a dedicated index on the priority column "failed miserably, actually causing Postgresql to stop responding" ([PriorityCalculator.java](https://github.com/apache/manifoldcf/blob/465b489/framework/pull-agent/src/main/java/org/apache/manifoldcf/crawler/system/PriorityCalculator.java); [JobManager.java](https://github.com/apache/manifoldcf/blob/465b489/framework/pull-agent/src/main/java/org/apache/manifoldcf/crawler/jobs/JobManager.java)).

| System | (a) Newly discovered first | (b) Known item refresh | Operator lever worth copying |
|---|---|---|---|
| Nutch | Chained float score (OPIC default), per-host cap after the sort | Adaptive: interval ×0.8 on change, ×1.4 unchanged, clamped; forced re-check at 90 days | `fixedInterval` metadata that the adaptive logic honours |
| StormCrawler / URLFrontier | `nextFetchDate = now`, FIFO per queue | Fixed 1 day, or adaptive `(1−d)·I + d·min` toward a floor | Per-URL preset date; per-key `BlockQueueUntil`, crawl limit |
| Heritrix | Precedence (cost or hops), queue precedence, session budgets | Fixed `rescheduleDelaySeconds`, overridable per site | Sheets by prefix or rule, `precedenceFloor` as "keep but never crawl" |
| BUbiNG | Per-host BFS, politeness only | None | Cache in front of the dedup store |
| Frontera / Scrapy | Fixed score tiers, hash bands, per-domain cap | Fixed 1-day interval (removed from master) | Hash-band interleaving |
| Common Crawl | Harmonic-centrality rank sets per-domain budgets | Implicit, by re-sampling | Rank-to-budget log interpolation, spam cluster heuristic |
| ManifoldCF | Per-bin log counter, round-robin across bins | Additive interval with min/max bounds | Throttle regexes, min/max recrawl interval |

Three refresh rules exist in this lineage, and none is value-aware. Nutch's adaptive multiplier ([AdaptiveFetchSchedule.java](https://github.com/apache/nutch/blob/master/src/java/org/apache/nutch/crawl/AdaptiveFetchSchedule.java)) pulls each interval toward that page's own change interval, which is proportional allocation in disguise. With the shipped 0.2/0.4 rates, a page that alternates changed and unchanged drifts *upward* by 0.8 × 1.4 = 1.12 per pair. Its error handling is worth keeping as-is. A transient error retries after a day up to 3 times, then the item becomes GONE with its interval ×1.5, and `db.fetch.interval.max` (90 days) forces a re-check of everything, so nothing is ever truly dropped ([nutch-default.xml](https://github.com/apache/nutch/blob/master/conf/nutch-default.xml); [AbstractFetchSchedule.java](https://github.com/apache/nutch/blob/master/src/java/org/apache/nutch/crawl/AbstractFetchSchedule.java)). My read across all seven systems is blunt. They solve politeness and fairness well and treat value as someone else's problem. The Directory needs their *mechanisms* (caps, floors, overlays, an indexed sort column) wrapped around the academic *scores*.

## Raw backlink counts lose to random; weighted, language-aware citers win

The largest controlled comparison of discovery orderings simulated full crawls of the .cl and .gr web. Measured as average cumulative PageRank, where random scores 0.50, **backlink-count scored 0.50 and partial PageRank 0.52**. Breadth-first reached 0.64, OPIC and larger-sites-first 0.67, and history-guided PageRank 0.70. The authors explain that backlink count and partial PageRank "tend to get stuck in pages that are locally optimal" ([Baeza-Yates et al. 2005](https://archives.iw3c2.org/www2005/proceedings/docs/p864.pdf)). OPIC itself is a one-pass, matrix-free PageRank. Each fetched node splits its cash equally over its out-links, and a frontier node's priority is the cash received, which makes it a *weighted* backlink count ([Abiteboul et al. 2003](https://cs.brynmawr.edu/Courses/cs380/fall2006/online_page_importance.pdf)). It is weak early in a crawl and topic-blind. In a focused-crawl benchmark it reached only **0.18 to 0.29** of an oracle-greedy score, while simple neighbourhood estimators reached 0.38 to 0.59 ([Gouriten et al. 2014](https://www.cl.cam.ac.uk/~ey204/teaching/ACS/R212_2015_2016/papers/gouriten_HT_2014.pdf)). The spam-resistant form of backlink counting counts only *cross-site* links ([Olston & Najork 2010](https://khoury.northeastern.edu/home/vip/teach/IRcourse/IR_surveys/olston-najork@web-crawling10.pdf)). Every Telegram channel is its own "site", so your **distinct citer count is already that form**, and your data confirms it predicts liveness monotonically (43%, 60%, 73%, 78%). Repeated mentions from one channel are the plain backlink count that lost to random.

The focused-crawling literature supplies the combination rule. Aggarwal et al. define an interest ratio `I(C,E) = P(C|E)/P(C)` per piece of evidence. Under independence the ratios multiply, so priority is a weighted sum of log ratios, `Σ w_k·log I_k`, which is naive-Bayes log-odds. On roughly 10,000-page crawls it harvested **33% to 41%**, where random harvested about 1% ([Aggarwal et al. 2001](https://archives.iw3c2.org/www10/cdrom/papers/110/index.html)). Applied to your marginals, forward against mention-only is a 3.3x ratio and 20+ citers against one citer is 1.8x. The bot suffix, at 0.3% live, costs **about 330 probes per live hit** and belongs in a hard gate, not a soft feature. The independence assumption is the weak spot, since forwarded channels probably also have more citers. That is why I'd estimate kind and citer count jointly in one cell table first, and move to a logistic regression on the probe log later. It has the same log-odds form, but its learned weights absorb the correlation and its outputs come out calibrated. Gouriten et al.'s incremental linear regression over cheap first-level estimators "performs well in the long run", and **log-smoothing the in-degree raised its correlation with true value from 0.063 to 0.269** ([Gouriten et al. 2014](https://www.cl.cam.ac.uk/~ey204/teaching/ACS/R212_2015_2016/papers/gouriten_HT_2014.pdf)). Use `log(1 + citers)`, never the raw count.

Relevance is a separate factor from liveness, and in your data it is the larger one. Probes of targets with a fa/en citer were 23% of probes but found 66% of the live fa/en channels. That is a per-probe yield of 66/23 = 2.9x the average, against 34/77 = 0.44x for everything else, a **6.5x gap** (my arithmetic on your numbers). The Telegram graph explains why the signal is so strong. TeraGram found **83.3% of forwards stay within one language** ([Golovin et al. 2026](https://arxiv.org/pdf/2605.15956)), so a citer's language predicts its target's language. It also explains the Russian drift you observed. Every published Telegram snowball crawl converged on the Russian graph: 56% Russian in TeraGram, 82% in TeleScope, 35.5% in TGDataset ([TeraGram](https://arxiv.org/pdf/2605.15956); [TeleScope](https://arxiv.org/html/2504.19536v1); [TGDataset](https://arxiv.org/html/2303.05345v3)). TeraGram's frontier was exactly "observed in-references from already downloaded chats", taking the maximum every time. That is the Maximum Observed Degree heuristic, which wins most budgeted comparisons but **stalls at 80-90% coverage** when two communities are joined by a thin bridge ([arXiv 2403.14351](https://arxiv.org/html/2403.14351v1)). Greedy in-degree on a mixed graph enters the biggest, densest community and stays there. Weighting each citation by the citer's language value turns that trap into a focused crawler pointed at the community you want.

Two more ideas from this literature are worth keeping. Shark-search passes a decayed relevance to children (`inherited = δ·sim(parent)`, else `δ·inherited(parent)`, with δ = 0.5 tuned on the web), so a crawl can still pass through irrelevant intermediaries ([Hersovici et al. 1998](https://archives.iw3c2.org/www7/programme/fullpapers/1849/com1849.html)). A soft language term with a non-zero floor does the same job and does not throw away the fa/en channel whose only citer is Russian. Yandex predicts the quality of a source's new pages from the quality of pages previously linked from that source ([Lefortier et al. 2013](https://arxiv.org/pdf/1307.6080)). For you that is **citer precision**, the share of a citer's probed targets that turned out live. Promo channels that list hundreds of dead handles reveal themselves through it, the same way Common Crawl caught a spam cluster that took **56M pages (1.5% of a crawl)** by flagging "low-ranking domains with too many outlinks or subdomains" ([Nagel 2023](https://markup.co.uk/hg/cc/work/raw-file/tip/nagel.230206.pdf)). Hop distance, the basis of Nutch's depth plugin and Heritrix's `HopsUriPrecedencePolicy`, carries no information here, because 99% of your entries are 3+ hops out.

## Refresh value saturates, so uniform beats proportional and exact counts beat bits

Cho and Garcia-Molina's result is the foundation. With Poisson changes and equal weights, freshness-optimal sync frequency is *non-monotone* in change rate: it rises, peaks, then falls to exactly zero for items that change too fast to track. **Uniform allocation beats proportional allocation for every rate distribution**, and they prove it. On 720,000 real pages, freshness was **0.12 proportional, 0.57 uniform and 0.62 optimal**, and age was **400 days, 5.6 days and 4.3 days** ([Cho & Garcia-Molina](https://www.kth.se/social/files/554f1d5bf27654514fd00393/synchronizing-a-database-to-improve-freshness.pdf)). Their summary rule, "when it is not possible to keep up with everything, it is better to focus on what we can track", matters at your scale. 507k live channels against 80k probes a day is a **6.3-day cycle even if refresh took the entire budget**, so most busy channels will always have unseen posts. Deterministic spacing also beats randomised visits at the same rate ([Cho & Garcia-Molina](https://www.kth.se/social/files/554f1d5bf27654514fd00393/synchronizing-a-database-to-improve-freshness.pdf); [Azar et al. 2018](https://www.erichorvitz.com/Crawl_1801519115.full.pdf)), which favours a stored next-due time over sampling.

Three independent derivations reach the same per-item value function. Olston and Pandey prove that for any monotone staleness curve D(t), the optimal policy refreshes an item once `U(t) = t·D(t) − ∫₀ᵗ D(x)dx` crosses a global threshold ([Olston & Pandey 2008](https://archives.iw3c2.org/www2008/papers/pdf/p437-olstonA4.pdf)). Google's 2025 paper and its production crawl apply this to binary freshness, `V(τ) = (w/λ)(1 − (1 + λτ)e^{−λτ})`, and take the argmax each slot, so no global solver is needed ([Busa-Fekete et al. 2025](https://arxiv.org/pdf/2502.02430v3); [Richoux 2018](https://www.unofficialgoogledatascience.com/2018/07/by-bill-richoux-critical-decisions-are.html)). The catch is that V is bounded by w/λ, so "some pages may never be recrawled". Azar et al.'s exact solution makes that concrete. It sets the rate to zero for every item with `w/λ ≤ λ*` ([Azar et al. 2018](https://www.erichorvitz.com/Crawl_1801519115.full.pdf)). Kolobov et al. call this "unacceptable in practice". They replace the binary penalty with a harmonic one, H(n) over n uncrawled changes, under which any policy that ignores a changing source has infinite cost. On 18.5M Bing URLs that **beat the binary-optimal policy by 35%** on harmonic cost without losing on binary cost. Change-rate-proportional crawling scored 2144 against uniform's 1268, a far worse result ([Kolobov et al. 2019](https://papers.nips.cc/paper_files/paper/2019/file/ad13a2a07ca4b7642959dc0c4c740ab6-Paper.pdf)). Yandex's ECHO, the closest analogue to Telegram because it recrawls "content sources" that emit new items, uses the same function. Its greedy variant ranks by expected new value accumulated since the last fetch, `λ·P·τ`, needs only a priority queue, and reached the profit ceiling at **one fifth of the crawl rate breadth-first needed** ([Lefortier et al. 2013](https://arxiv.org/pdf/1307.6080)).

Change-rate estimation is where Telegram is easier than the web. A web fetch says only "changed or not". The naive estimator counts at most one change per interval and is biased low, which is why Cho and Garcia-Molina's corrected estimator `λ̂ = −log((n − X + 0.5)/(n + 0.5))/I` and an implicit MLE equation exist ([Grimes & O'Brien 2008](https://archives.iw3c2.org/www2008/papers/pdf/p1149-grimes.pdf); [Kolobov et al. 2019](https://papers.nips.cc/paper_files/paper/2019/file/ad13a2a07ca4b7642959dc0c4c740ab6-Paper.pdf)). Your fetch reports `N_j = latest_id_now − latest_id_prev`, an observed *count*. If posts are Poisson with rate λ, `N_j ~ Poisson(λ·a_j)` and the MLE is just `Σ N_j / Σ a_j`. It is unbiased at any fetch interval and needs no root-finding. A gamma prior gives smoothing and cold start in one formula, `(α₀ + Σ N)/(β₀ + Σ a)`. Kolobov's "+0.5 imaginary observation" is the special case α₀ = β₀ = 0.5. These derivations are mine, standard Poisson statistics rather than a crawl-paper result. Two caveats apply. Deleted posts consume ids, so the count overcounts slightly, and TeraGram warns that message ids are unreliable join keys after deletions ([Golovin et al. 2026](https://arxiv.org/pdf/2605.15956)). Real rates also drift and show daily periodicity ([Grimes & O'Brien 2008](https://archives.iw3c2.org/www2008/papers/pdf/p1149-grimes.pdf)), so the sums should decay. The first probe of a channel already carries 13 to 20 timestamped posts, which gives a cold-start rate before any second visit exists.

## Nobody has solved the split, and strict priority is how refresh starved

On splitting one budget between discovery and refresh, the survey literature is explicit: "There is no consensus about the best way to balance the two", and some treat it as "a business decision" ([Olston & Najork 2010](https://khoury.northeastern.edu/home/vip/teach/IRcourse/IR_surveys/olston-najork@web-crawling10.pdf)). The two published unifications are WebFountain, which treats uncrawled pages as freshness zero, and OPIC, which shifts cash through a virtual page to favour one side ([Abiteboul et al. 2003](https://cs.brynmawr.edu/Courses/cs380/fall2006/online_page_importance.pdf)). Neither gives a number. None of the seven production systems documents a split either. Nutch's `generate.restrict.status`, which restricts a run to one status, is the closest thing to a mode switch ([Generator.java](https://github.com/apache/nutch/blob/master/src/java/org/apache/nutch/crawl/Generator.java)). Yandex found that fixed quotas were "far from being optimal", but it compared them against a solver priced in a single currency (clicks) ([Lefortier et al. 2013](https://arxiv.org/pdf/1307.6080)). You do not have one currency. "A new relevant live channel" and "a stale channel's missed posts" are apples and oranges until the Owner states an exchange rate.

Refresh is also your *discovery source*, which changes the arithmetic. Dasgupta et al. showed that **90% of new pages can be found by monitoring a small, well-chosen set of old pages**, and that the last 10% costs far more ([Olston & Najork 2010](https://khoury.northeastern.edu/home/vip/teach/IRcourse/IR_surveys/olston-najork@web-crawling10.pdf); [Dasgupta et al. 2007](https://www.www2007.cpsc.ucalgary.ca/papers/paper592.pdf)). A refresh of a channel that historically cites many new fa/en handles is worth more than its freshness alone, and that harvest yield belongs in its refresh weight. The current rule, where new handles strictly outrank refreshes, is the same failure as Azar's zero rates and the binary-freshness cutoff, applied one level up. Whichever class sorts second gets nothing whenever the first is non-empty, and with roughly a million mined handles the discovery side never empties.

Exploration is the other piece the literature handles unevenly. Gouriten et al. found that randomised "altered greedy" falls behind pure greedy beyond a few thousand steps, *when the estimator is good and the graph is homophilous*. They also found that re-scoring only every b fetches costs **8.3% to 35.9%**, and "even for a batch size of 2" the loss is notable ([Gouriten et al. 2014](https://www.cl.cam.ac.uk/~ey204/teaching/ACS/R212_2015_2016/papers/gouriten_HT_2014.pdf)). Menczer et al. reached the opposite emphasis: "best performance came from a novel combination of explorative and exploitative bias" ([Menczer et al. 2004](https://experts.illinois.edu/en/publications/topical-web-crawlers-evaluating-adaptive-algorithms/)). Diligenti's context graphs improved long-term coverage "by not being overly greedy" ([Olston & Najork 2010](https://khoury.northeastern.edu/home/vip/teach/IRcourse/IR_surveys/olston-najork@web-crawling10.pdf)). Anthelion combines an online classifier with a bandit that picks which domain to visit ([Nutch wiki: Anthelion](https://cwiki.apache.org/confluence/spaces/NUTCH/pages/115512015/Anthelion)). My resolution for your case: the risk is not a weak estimator in general but a *biased training set*, because a greedy crawler only collects labels for the handles it already likes. Leskovec and Faloutsos found uniform random node selection does "surprisingly well" ([Leskovec & Faloutsos 2006](https://www.cs.upc.edu/~CSN/bib/LeskovecFaloutsos2006.pdf)), and random crawling escapes the community trap that MOD cannot ([arXiv 2403.14351](https://arxiv.org/html/2403.14351v1)). A small uniform-random slice therefore crosses bridges and calibrates the model at once. No crawling paper I found evaluates Thompson sampling or UCB on this problem, so a per-cell bandit is an upgrade path, not the starting point.

## A recommended design for the Directory

What follows is a design inference from the sources above, not a published system. Where a formula is my derivation rather than a paper's, the text says so.

### Discovery score: expected wanted channels per probe

```
EV(h)      = gate(h) · boost(h) · P(live | x_h) · Σ_ℓ v_ℓ · P(lang = ℓ | live, x_h)

gate(h)    = 0 if handle ends in "bot" (case-insensitive) or fails ^[a-z0-9_]{5,32}$, else 1
P(live|x)  = (live_cell + 1) / (probed_cell + 2)
             cell = best_kind {forward, reply, link, mention-only} × distinct-citer bucket {1, 2-4, 5-19, 20+}
P(ℓ|live,x)= (Σ_c a_c · [lang_c = ℓ] + m·π_ℓ) / (Σ_c a_c + m),   m = 2, π_ℓ = language share among live entries
a_c        = q_c / log2(2 + out_c)                     weight of distinct citer c
q_c        = (live targets of c + 1) / (probed targets of c + 2)    citer precision
out_c      = distinct handles c references
v_ℓ        = operator language values, default fa 1.0, en 1.0, ru 0.15, other 0.1
priority   = round(1e6 · EV)                           the existing integer column
```

Each term has a source. The cell table is Aggarwal's interest ratio, estimated jointly over kind and citer bucket so those two correlated signals are not double-counted, with Laplace smoothing so empty cells are not 0 or 1. The language term is citer-language evidence backed by TeraGram's 83.3% same-language forwards. Its pseudo-count floor `m·π_ℓ` is the Shark-search decay that keeps a Russian-cited Persian channel reachable. `a_c` is OPIC's split by out-degree, damped by a logarithm so a large aggregator still counts, and multiplied by Yandex-style citer precision. Recompute EV from the *current* citation table every time and never accumulate it, which is the fix for Nutch's OPIC inflation. Recompute only the handles whose citation set changed after each harvest batch (Gouriten's re-scoring result), and run a full pass nightly because `q_c` moves. A nonzero `v_ru` keeps the Directory's Russian coverage alive at a fraction of the budget instead of zero.

The stage-two upgrade, once a few weeks of exploration labels exist, is a multinomial logistic regression over the outcomes {dead/not a channel, live-fa, live-en, live-ru, live-other}. It reads P(live, ℓ | x) directly. Its features are kind indicators, `log(1 + distinct citers)`, `log(1 + Σ a_c)`, citer-language shares, the maximum citer's log subscribers, days since the newest citation, and handle shape (length, digits, underscores). The URL-classification literature supports that last group, since letter n-grams beat tokens for URL-only prediction ([Baykan et al. 2009](https://infoscience.epfl.ch/record/136823/files/Topic_www_09.pdf?version=1)). Train it weekly, only on the exploration slice or with that slice held out for calibration.

### Refresh score: an exact-count rate inside a concave utility

```
On every observation j of channel i (Directory probe, or a user sync if it sees latest_id):
  N_j = latest_id_j − latest_id_{j−1}           new posts (slight overcount from deletions)
  a_j = days since the previous observation
  d   = exp(−a_j / H),  H = 60 days             forget old evidence
  S_i = d·S_i + N_j ;   T_i = d·T_i + a_j
  λ̂_i = (α_i + S_i) / (β_i + T_i)              α_i, β_i from the first probe: (k−1) posts over their span, span capped at 30 days

Refresh value after τ days:
  U_i(τ) = w_i · ( τ − ln(1 + λ̂_i·τ) / λ̂_i )
  w_i    = boost_i · v_lang(i) · (1 + log10(1 + subscribers_i)) · (1 + η·ŷ_i),   η ≈ 1
  ŷ_i    = (new wanted handles first seen in i's refreshes + 1) / (refreshes of i + 5)

Schedule at write time:
  τ*_i      solves U_i(τ*) = Λ   (U is increasing in τ; Newton or bisection)
  next_due_i = t_last + clamp(τ*_i, 1 day, 60 days)
  Λ          weekly bisection so that Σ_i 1/τ*_i ≈ R_refresh (refresh probes per day)
Dequeue:    WHERE class = refresh AND next_due <= now() ORDER BY next_due LIMIT k_refresh
```

U is Olston and Pandey's threshold utility applied to the divergence `D(t) = ln(1 + λt)`, a smooth stand-in for Kolobov's expected harmonic penalty. The derivation is mine and untested on real data, but its limits are the published ones. When λτ is small, U ≈ wλτ²/2, identical to Google's binary-freshness value, so slow channels wait quadratically longer. When λτ is large, U ≈ wτ, uniform per unit weight, which is Cho's uniform-beats-proportional result. Unlike the binary value, it never saturates, so no channel starves. Worked at τ = 7 days and w = 1: a channel posting 10 times a day scores 6.57, a daily poster 4.92, a weekly poster 2.15 and a near-silent channel (0.01 a day) 0.23. Under proportional allocation the first two would differ by 10x. Here they differ by 1.34x. Storing `next_due` at write time follows StormCrawler's design and avoids recomputing a transcendental function over 507k rows on every tick. The `ŷ_i` term is Dasgupta's insight: refresh the channels that keep revealing new handles. The 60-day cap is Nutch's `db.fetch.interval.max` idea, there so dead or revived channels get noticed.

Status changes run through their own state machine and never touch λ̂, Nutch-style. A transient error retries after a day, up to 3 times, then the channel becomes dead. A dead channel is rechecked after 30 days, with the interval ×1.5 per further miss, capped at 180 days. A handle that redirects away from `/s/` (a user, bot or unregistered name) is rechecked after 180 days, because Telegram recalls unused usernames and collectible usernames move between peers ([Telegram FAQ](https://telegram.org/faq); [Telegram API: Fragment](https://core.telegram.org/api/fragment)).

### Capacity: explicit shares, work-conserving, with a catch-up mode

Let B be the Directory's daily probe budget after user-facing syncs, about 80k today. Split it with an Owner-set refresh share r. Default to **r = 0.5** in steady state, and switch to **0.65 in catch-up mode** while more than 10k live channels are 7 or more days past `next_due`. Discovery takes 1 − r, and **10% of discovery is exploration**. Each tick takes its quota from both selections. Slots one side cannot fill (no due refreshes, or no handle above the discovery floor `EV_min`, the Directory's version of Heritrix's `precedenceFloor` and Nutch's `generate.min.score`) flow to the other side, so the budget never idles. Here is the arithmetic behind 0.5. At 40k refreshes a day the *mean* interval over 507k channels is 12.7 days. Value weighting turns that into roughly weekly for the top quarter (127k ÷ 7 ≈ 18k a day) and about a month for the rest (380k ÷ 30 ≈ 12.7k a day), which leaves headroom for silent-channel rechecks. That is my sizing, not a published number. Re-tune r weekly from two dashboard figures: wanted live channels per probe in the lowest-priority decile actually probed, and the overdue count. Two fairness caps sit inside the discovery selection. No more than K handles per batch may share the same top-weight citer (`row_number() OVER (PARTITION BY top_citer ORDER BY priority DESC) <= K`, the StormCrawler SQL-spout pattern). Start with a constant K = 20. Common Crawl's log interpolation from rank-1 to tail citers is the upgrade if a constant proves too blunt. Index `(class, priority DESC)` and `(class, next_due)` from day one, which is ManifoldCF's lesson.

### Exploration: a random slice that keeps the model honest

The exploration slice draws handles uniformly at random from the gated, unprobed frontier. It has two jobs. It crosses into communities the greedy score has not seen yet, and it produces unbiased labels, because without it every training example comes from handles the model already preferred. Log `explored = true` on each probe and report its live and wanted rates beside the greedy ones. When the greedy decile's yield falls toward the random slice's yield, the estimator has stopped adding value and needs retraining. If the slice proves too blunt, the upgrade is Thompson sampling over the 4 × 4 × 3 cells (kind × citer bucket × citer-language mix), drawing from each cell's Beta(wanted + 1, unwanted + 1) posterior. New live channels need no refresh exploration, because the first probe's visible posts already seed λ̂. Give each one a guaranteed second probe at 7 days to anchor the count estimator.

### Operator controls: rules as overlays, not rewritten scores

Model controls on Heritrix sheets. A rule is a predicate plus an effect plus an order, stored in its own table and applied when EV, w and `next_due` are computed. Rules are never baked into the learned score, so a model retrain cannot erase them. That keeps clear of Nutch's injector, which silently *averages* a re-injected boost with the old score ([Injector.java](https://github.com/apache/nutch/blob/master/src/java/org/apache/nutch/crawl/Injector.java)). Predicates reuse the Directory tab's existing filters: language, subscriber and posts-per-week bounds, Tags, Seeds, Shared parents or children of Seeds or Tags, reference kind, a handle pattern, and explicit ids from ticks and the bulk bar. Boost multipliers combine by product across matching rules. For the other fields the last matching rule in order wins.

| Effect | Applies to | Precedent |
|---|---|---|
| Boost ×k (also ×0.2 to demote) | EV and w | Heritrix `basePrecedence` overlay; Nutch injected score |
| Exclude (kept, listed, never probed) | both | Heritrix `precedenceFloor` |
| Fixed interval (e.g. daily) | refresh | Nutch `fixedInterval` (NUTCH-1388) |
| Min / max interval | refresh | ManifoldCF recrawl bounds; Nutch per-host interval file |
| Daily probe cap for the predicate | both | URLFrontier `SetCrawlLimit`; Common Crawl per-domain budget |
| Probe now (one-shot) | both | StormCrawler preset `nextFetchDate` |
| Language values v_ℓ, refresh share r, exploration ε, EV floor | global settings | Common Crawl limits file; Nutch `restrict.status` |

Each row should get a "why this priority" breakdown showing P(live), the language term, w, λ̂, the matching rules and `next_due`. Google's crawl team chose "an understandable heuristic" over a large solver for exactly this reason ([Richoux 2018](https://www.unofficialgoogledatascience.com/2018/07/by-bill-richoux-critical-decisions-are.html)). Add one metric StormCrawler only proposed after the fact: probes per day by class, by exploration flag and by language ([issue #2185](https://github.com/apache/stormcrawler/issues/2185)).

### Pitfalls and their guards

| Pitfall | Evidence | Guard in this design |
|---|---|---|
| OPIC score inflation | Nutch's OPIC never decays and the parent keeps its cash; "can't recrawl" without inflation ([Fixing OPIC](https://cwiki.apache.org/confluence/spaces/NUTCH/pages/115512062/FixingOpicScoring)) | EV recomputed from the current citation table, never accumulated |
| Backlink-count trap | 0.50 vs random 0.50; stuck in locally dense regions ([Baeza-Yates 2005](https://archives.iw3c2.org/www2005/proceedings/docs/p864.pdf)); Russian drift in every Telegram snowball | Distinct citers, log-damped, precision- and language-weighted, capped per citer |
| Proportional allocation | Freshness 0.12 vs 0.62 ([Cho & Garcia-Molina](https://www.kth.se/social/files/554f1d5bf27654514fd00393/synchronizing-a-database-to-improve-freshness.pdf)); Nutch's ×0.8/×1.4 converges to it | Concave U; no multiplicative interval rule |
| Starvation | Binary-optimal rates are zero for low-value fast items ([Azar 2018](https://www.erichorvitz.com/Crawl_1801519115.full.pdf)); strict class order left 123k overdue | Non-saturating U, explicit shares with overflow, 60-day max interval |
| Stale scores | Re-scoring every 2+ fetches cost 8-36% ([Gouriten 2014](https://www.cl.cam.ac.uk/~ey204/teaching/ACS/R212_2015_2016/papers/gouriten_HT_2014.pdf)) | Incremental re-score after each harvest batch |
| Biased labels | Greedy only labels what it already likes | Random slice, flagged and held out |
| Spam and promo citers | Common Crawl's 56M-page spam cluster; fake fediverse peers ([Simon Willison](https://simonwillison.net/2024/Jan/12)) | Citer precision q_c, out-degree damping, per-citer cap |
| Code and config defaults disagree | Nutch `inc_rate` 0.2 in code vs 0.4 in XML; StormCrawler error interval 44640 vs -1 | One defaults source (`Settings`), with a test |
| Unindexed million-row sort | ManifoldCF froze Postgres | Indexes on `(class, priority)` and `(class, next_due)` |
| Handle recycling | Telegram recalls usernames; collectibles move ([FAQ](https://telegram.org/faq)) | Dead and non-channel states rechecked on a long cap, never deleted |

## Conclusion

The literature changes one framing above the rest. "New handles versus refreshes" is not a ranking question. It is a budget question with no published answer, and a strict ranking between two classes reproduces the starvation the refresh papers spent two decades removing from within a single class. The best ideas also invert the usual weighting of signals. Who cites a handle (its language, its track record, how many distinct channels) predicts value better than how often or how it is cited, and the Directory's real objective, wanted channels per probe, rewards relevance more than liveness. Telegram's exact post counts make the refresh side easier than anything the web literature faced, so the remaining risk sits in the untested parts. The log-penalty utility, the citer-language proxy and the 0.5 share all rest on inference. The random slice and the per-class dashboard exist to test them.

The single cheapest change with the largest expected effect is to stop letting discovery strictly outrank refresh. Even before any new score ships, a fixed refresh share with overflow drains the 123k backlog and turns the rest of this design into incremental work.
