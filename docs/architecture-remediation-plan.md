## 1. Context — why this work exists

This app began life as a **pure browser application**: it fetched whole datasets into
IndexedDB and did all filtering, sorting, searching and aggregation in JavaScript. A FastAPI
backend was later grafted on, scaffolded from
[fastapi/full-stack-fastapi-template](https://github.com/fastapi/full-stack-fastapi-template).
The migration kept the FastAPI/SQLModel substrate but **dropped the template's pagination
discipline** — the template's `skip`/`limit`/count-wrapper convention survives only in the
two routers nobody adapted (`/items`, `/users`).

The result: the frontend still behaves like a browser-only app, and the backend happily
serves it unbounded data.

This surfaced as a production incident on staging (4 vCPU / 7 GB): backend workers at
**3.09 GB RSS**, load average 7+, Postgres connections idle-in-transaction for 2+ minutes,
workers being killed and respawned. Root cause: `GET /posts` has **no LIMIT** and optional
date bounds, against a **2.97M-row** `tg_posts` table with **962 followed channels**.

Two investigations preceded this plan and are committed in the repo:
- `docs/discover-bulk-follow-load-investigation.md` — the incident, py-spy methodology, root cause.
- `docs/frontend-backend-boundary-audit.md` — the systemic survey.

**⚠️ Both documents contain errors that this plan supersedes. See §3.**

**Intended outcome:** every endpoint bounded, every expensive aggregation computed in SQL,
no runaway client loops, and the frontend asking for what it needs instead of everything.

### Conventions you must follow

- **Alembic revision IDs are hand-rolled**, not autogenerated hashes. The chain shifts each
  letter-digit pair forward: `p8q9r0s1t2u3` → `q9r0s1t2u3v4` → next is **`r0s1t2u3v4w5`**.
  **Current head is `q9r0s1t2u3v4`.** After `--autogenerate`, hand-edit `revision` and
  `down_revision`. Filename: `<revision>_<snake_case_slug>.py`.
- **Backend tests have NO per-test transaction rollback.** A session-scoped `db` fixture
  commits directly; isolation comes from an autouse fixture truncating all `tg_*` tables
  **after** each test. Never rely on data surviving across tests.
- **API tests use real auth**, no `dependency_overrides`. Copy this helper verbatim:
  ```python
  def _auth(client: TestClient) -> dict[str, str]:
      login = client.post(
          f"{settings.API_V1_STR}/login/access-token",
          data={  # form-encoded, NOT json=
              "username": settings.FIRST_SUPERUSER,
              "password": settings.FIRST_SUPERUSER_PASSWORD,
          },
      )
      return {"Authorization": f"Bearer {login.json()['access_token']}"}
  ```
- **Frontend tests are `bun:test`**, colocated as `*.test.ts` next to the source, under `src/`
  (`bun test src` only scans `src/`). Use the `@/` alias. Component tests use
  `renderToStaticMarkup` from `react-dom/server` — there is no jsdom/testing-library.
- **Pre-commit uses `prek`.** Ruff and biome **auto-fix then exit non-zero**, so your first
  `git commit` after editing will usually fail — `git add` the rewritten files and re-commit.
  `mypy`/`ty` run over the **entire** `backend/app` tree, so an unrelated pre-existing type
  error will block you. Ruff bans `print()` (`T201`) outside `scripts/`.
- **`generate-frontend-sdk` pre-commit hook** auto-regenerates the client on any `backend/**`
  change. Generated output **is committed**. It must be generated with the default
  `ENVIRONMENT=production` — never commit a client generated with `ENVIRONMENT=local`.

3. `bunx tsc -p tsconfig.build.json --noEmit` excludes test files by design. Use it — the

- **The single worst issue in the codebase** — `frontend/src/contexts/ScraperContext.tsx:238-274`

## 6. Phase 1 — Stop the runaway loops

*Independent files. Fully parallel. No backend changes. Ship this first — it is the only phase
where the bugs actively burn CPU with no user action.*

### T1.1 — Background language detection: unbounded fetch in an infinite loop ⚠️ HIGHEST SEVERITY

**File:** `frontend/src/contexts/ScraperContext.tsx:238-274`

**Problem.** 5 seconds after mount, for **every** channel with no `language`, sequentially:
```ts
const recentPosts = await getPostsByDateRange([channel.name], 0, Date.now())
const lang = detectLanguageFromPosts(recentPosts)
```
- `0, Date.now()` = that channel's **complete post history**, one round trip per channel.
- `detectLanguageFromPosts` (`frontend/src/lib/language.ts:11`) does `posts.slice(0, 20)` —
  **≥99% of every payload is discarded immediately.**
- **It never terminates.** The effect deps include `channels`; it ends with `await loadChannels()`
  which invalidates the channels query → new array identity → effect re-runs. Channels where
  `detectLanguageFromPosts` returns `undefined` (sample <20 chars, or `franc` says `und`) never
  get `upsertChannel` called, so they stay in the list and are rescanned **every ~5s forever**.

**Fix.** Two parts, both required:
1. **Terminate the loop.** Track attempted channel names in a ref and skip them; never retry a
   channel whose detection returned `undefined` within the session. Stabilise the effect deps so
   it does not re-arm on every `channels` identity change.
2. **Stop over-fetching.** Only 20 posts are needed. Depends on **T2.1** for a bounded endpoint —
   until then, at minimum cap the date range. Best end state: move language detection
   **server-side at ingest** (the scraper already has the post text) and delete this effect
   entirely. If you do that, add a small backfill job and note it for review.

**Verify.** Add `frontend/src/lib/language.test.ts` covering the "detection returns undefined →
channel is not retried" logic (extract that decision into a pure helper so it is testable).
Then: `cd frontend && bun test src && bunx tsc -p tsconfig.build.json --noEmit`.
Manually: run the app, watch the network tab — there must be **no repeating burst of `/posts`
requests** at rest.

### T1.2 — NetworkTelemetry self-sustaining refetch loop

**File:** `frontend/src/components/NetworkTelemetry.tsx:25-48`

**Problem.** `loadData` is a plain arrow function (not `useCallback`), and the effect depends on
it, so it re-runs on every render; `setLogs(...)` produces a new array → new render → refetch.
The `setInterval(loadData, 10000)` is nearly irrelevant. Also aggregates (`totalRequests`,
`successRate`, `rateLimits`, lines ~52-60) are recomputed in JS over the full log set per tick.
Mitigating: only mounted on two settings sub-tabs (`SettingsHub.tsx:251,270`).

**Fix.** Replace the bespoke fetch+interval with the existing
`useNetworkLogsQuery` (`frontend/src/hooks/useLogs.ts:64`, keyed `queryKeys.logs.network`,
already used by `DataContext.tsx:144`) and set a `refetchInterval`. This gets TanStack Query's
de-duplication for free and deletes the hand-rolled loop.

**Verify.** `bun test src`, typecheck, then open Settings → Network Telemetry and confirm in the
network tab that requests happen on a steady interval, not continuously.

### T1.3 — `useApiStatus`: 7 independent timers

**File:** `frontend/src/hooks/useApiStatus.ts:22`

**Problem.** The hook holds no shared state, so each of its 7 consumers (App, ScraperContext,
AIContext, DiscoverView, SummaryView, ChannelGrid, useCommandRegistry) mounts its own 30s
`setInterval` → up to 7 health checks per 30s and 7 diverging `isOffline` values.

**Fix.** Convert to a single TanStack Query (`queryKey: ["health"]`, `refetchInterval: 30_000`)
so all consumers share one request and one value. Add a `health` key to
`frontend/src/hooks/queryKeys.ts`. Keep the hook's public API identical so no consumer changes.

**Verify.** `bun test src`, typecheck, and confirm exactly one health-check request per 30s in
the network tab with several consumers mounted.

## 7. Phase 2 — Bound every unbounded endpoint (backend only)

*All backend. `data.py` is contended — see §5. Follow `_list_logs_page` for every list endpoint.*

### T2.1 — Paginate `GET /posts` ⚠️ FOUNDATIONAL — several later tasks depend on it

**Files:** `backend/app/services/posts.py:97-111`, `backend/app/api/routes/data.py:492-511`

**Problem.** No LIMIT, optional date bounds, `session.exec(stmt).all()` over 2.97M rows.
This is the root cause of the production incident.

**Fix.** Mirror the logs pattern exactly:
- Add module constants `DEFAULT_POST_PAGE_SIZE = 500`, `MAX_POST_PAGE_SIZE = 5000`.
- `list_posts(..., limit: int, offset: int)` with `.order_by(Post.timestamp.desc())`
  (**deterministic ordering is required** — without it, offset paging silently repeats/skips rows),
  `.offset(offset).limit(limit)`.
- Route: `limit: int = Query(default=DEFAULT_POST_PAGE_SIZE, ge=1, le=MAX_POST_PAGE_SIZE)`,
  `offset: int = Query(default=0, ge=0)`.
- An index already exists: `ix_tg_posts_channel_name_timestamp (channel_name, timestamp DESC)` —
  ordering by `timestamp DESC` uses it. **Do not add a new index.**

**Verify.** New `backend/tests/api/test_posts_pagination.py`, modelled on
`backend/tests/api/test_sync_logs_pagination.py`: newest-first, limit caps, offset pages,
default applies, `limit` bound enforced (422 above max). Then `cd backend && uv run pytest tests/ -q`.

### T2.2 — Bulk post lookup endpoint

**Problem.** `repository.ts::getPost` fetches a channel's whole history to return one post,
called in a loop (`frontend/src/services/rag.ts:41`) and per citation hover
(`frontend/src/components/CitationHover.tsx:33`). **No single/bulk post endpoint exists.**

**Fix.** Add `POST /data/posts/lookup` taking `[{channelName, postId}, ...]` (cap the batch,
e.g. 200) and returning matching posts via a single query using a tuple `IN` / `or_` of
`(channel_name, post_id)` pairs. Service fn in `backend/app/services/posts.py`.

**Verify.** New test: returns exactly the requested posts, ignores unknown pairs, rejects
over-cap batches (422).

### T2.3 — Single-translation endpoint + bound `list_translations`

**Files:** `backend/app/services/data_vectors.py:61-64`, `backend/app/api/routes/data.py:667`

**Problem.** `list_translations` has no LIMIT, and **no single-translation endpoint exists** —
which is why the frontend downloads the whole table to read one row.

**Fix.** Add `GET /data/translations/one?channelName=&postId=&language=` returning one row or
404/null. Separately add `limit`/`offset` to the list endpoint (logs pattern).

**Verify.** Test both: single lookup hit and miss; list respects limit/offset.

### T2.4 — `list_embeddings`: dead code, decide and act

**Files:** `backend/app/services/data_vectors.py:19-20`, `backend/app/api/routes/data.py:650`

**Problem.** Unbounded, but **zero frontend callers**. Purely theoretical risk today.

**Fix.** Preferred: **delete** the endpoint and service function (it is dead). If anything
outside `frontend/src` depends on it (check `backend/`, scripts, docs first), instead add
`limit`/`offset` per the logs pattern. **State in your PR/commit which you did and why.**

**Verify.** `cd backend && uv run pytest tests/ -q` plus a grep proving no remaining callers.
If deleted, regenerate the client (`bash scripts/generate-client.sh` from repo root).

### T2.5 — `GET /data/tag-runs`: light list projection + pagination

**Files:** `backend/app/services/tag_runs.py:39-41`, `backend/app/api/routes/data.py:554`

**Problem.** Unbounded, and each `TagRun` carries `promptText` (a **full serialized post corpus**),
plus `responseText`, `suggestions`, `allTagsSnapshot`. Fetching all runs re-downloads every
historical prompt corpus — tens of MB.

**Fix.** Two parts: (a) add `limit`/`offset`; (b) make the **list** endpoint return a light
projection (`id`, `createdAt`, `status`, `source`/`mode`, `postCount`) and add
`GET /data/tag-runs/{id}` returning the full row including heavy fields.

**Verify.** Test that the list response does **not** contain `promptText`, that the detail
endpoint does, and that limit/offset work.

### T2.6 — RAG search: N+1 query, silent truncation, Python-side date filter

**File:** `backend/app/api/routes/rag.py:106-122`

**Problem.** Three distinct bugs:
1. **N+1:** a separate `SELECT` per embedding inside the loop — with
   `RAG_SCAN_LIMIT_MAX = 5000` (`backend/app/core/config.py:155`) that is up to **5000 queries
   per search request**.
2. **Silent truncation:** `.limit(5000)` with **no `ORDER BY`** — past 5000 embedded posts,
   search silently scans an arbitrary DB-order subset and never says so.
3. **Date filter applied in Python *after* the cap** — a narrow date range can return almost
   nothing while matching posts exist.

**Fix.** Collapse the N+1 into one query (join, or collect keys then a single tuple-`IN`).
Push `start_date`/`end_date` into the SQL `WHERE`. Add a deterministic `ORDER BY` before
`.limit()`. Surface truncation in the response (e.g. a `truncated: bool`) so it stops being
silent. **pgvector is the correct long-term answer — note it as follow-up, do not attempt here.**

**Verify.** Test: date filtering returns correct results when matching posts sit beyond the
scan cap; result count/order is stable across identical calls; assert query count does not
scale with result count (use a SQLAlchemy event counter or `caplog`).

### T2.7 — `logs.py` bulk deletes

**File:** `backend/app/services/logs.py:193-232`

**Problem.** `clear_logs` and `delete_old_logs` do `select(model)).all()` then loop
`session.delete(row)`. Only reachable from user-triggered endpoints (`data.py:824`, `:847`) —
the scheduled sweep is already fixed — but the same OOM shape.

**Fix.** Rewrite both with bulk `sa_delete(...)` + `result.rowcount`, copying
`backend/app/jobs/retention.py::run_retention_cleanup`. Preserve the existing return shapes
(`int` / `dict[str, int]`) and the operator-scoping `user_id` filter.

**Verify.** Test both return correct counts and actually delete, with operator scoping intact.

`lib/commands/search-filters.ts:51`).

**Fix.**

2. Update `getPostsByDateRange` for the paginated `GET /posts` from T2.1 — either page through
   to satisfy existing callers, or expose an explicitly bounded signature and update callers.
   **Whichever you choose, no caller may silently receive truncated data believing it is complete.**
3. Update `frontend/src/api/data.ts::getPosts` to pass `limit`/`offset`.

**Verify.** New `frontend/src/lib/repository.test.ts` proving two concurrent calls with identical
params produce **one** underlying fetch. Then `bun test src`, typecheck, lint.

### T3.2 — Replace `getPost` full-history scans with the bulk lookup

### T3.4 — `TagContext`: lazy + light

**File:** `frontend/src/contexts/TagContext.tsx:86-95`

**Problem.** `listTagRuns()` in `useEffect(..., [])` with `TagProvider` mounted unconditionally
(`components/TgProviders.tsx`) → fires on **every page load** regardless of whether the Tag tab

**Fix.** Move to TanStack Query with `enabled` gated on the Tag view being active (copy the

## 9. Phase 4 — Push aggregation into SQL

*The "solve it the right way" phase. Each task removes a whole class of over-fetching.*

### T4.1 — Server-side Discover candidates ⚠️ THE ORIGINAL MOTIVATING PROBLEM

**Current state.** `frontend/src/lib/posts/discover-candidates.ts` fetches **all post bodies**
for the selected channels/date range, then extracts forwards/mentions/links and aggregates in
JS — to produce a handful of counts.

**Fix.** Add `GET /data/discover/candidates?channelNames=&startDate=&endDate=&signals=` returning
only aggregated rows: `{name, displayName, counts:{forward,mention,link}, total, seenIn[],
seenInCount, lastSeen, isFollowed, samplePost}`.

Port the extraction logic to Python. **Reuse what already exists** — do not rewrite:
- `backend/app/services/telegram_web.py::is_channel_handle`, `RESERVED_TELEGRAM_PATHS`
- `backend/app/services/post_links_parser.py::channel_from_telegram_url`
- `Post.forwarded_from` (forwards) and `Post.links` (masked links, already extracted at scrape time)
- Mentions still need a text regex — mirror
  `frontend/src/lib/posts/telegram-handles.ts::extractMentions` exactly, **including the email
  false-positive guard** (`@` must not follow a word character).

**Preserve these semantics** (they are already unit-tested on the frontend — port the tests):
per-post-per-kind dedup; **self-references excluded** (candidate handle == authoring channel);
case-insensitive handle dedup; invite/private/reserved paths excluded.

**Verify.** Port `frontend/src/lib/posts/discover-candidates.test.ts` cases to
`backend/tests/services/test_discover_candidates.py`. **Parity check:** for a seeded dataset,
the endpoint's output must equal the current frontend computation. Then update `DiscoverView` to
consume the endpoint and delete the now-dead client aggregation.

### T4.2 — Per-channel post counts in SQL

**File:** `frontend/src/lib/channels/sort-channels-for-grid.ts:91` (`buildPostsInScopeCounts`)

**Problem.** Tallies per-channel counts by iterating the full fetched posts array — a
`GROUP BY channel_name` done in JS.

**Fix.** Add `GET /data/posts/counts?channelNames=&startDate=&endDate=` returning
`{channelName: count}` via a SQL `GROUP BY`. Update the two consumers (`ChannelGrid.tsx:111`,
`lib/commands/extended-commands.ts:198`).

**Verify.** Backend test for correct grouping/filtering; frontend unit test for the consumer.

### T4.3 — Server-side channel search/filter

**Problem.** The full channel list (962+) is fetched unfiltered every time and then
searched/filtered in JS **in two independent places**:
`frontend/src/lib/channels/filter-channels-for-grid.ts` and
`frontend/src/lib/commands/filter-channels.ts`. `channel-tags.ts:62` is O(tags × channels).

**Fix.** Add query params to `GET /data/channels` (`search`, `group`, `language`, `tag`,
`limit`, `offset`) and consolidate both call sites onto them.
**Judgement call:** 962 rows is not 3M — this is the *least* urgent item in the phase. If the
channel list stays small, server-side tag-chip counts (a SQL aggregate) may be the only part
worth doing. **Measure before rewriting both UI surfaces**, and say what you measured.

**✅ CLOSED BY MEASUREMENT (2026-07-22).** Measured on the live DB: **780 channels,
~135 kB** of row data (≈250–400 kB as JSON). `GET /data/channels` is fetched **once
per session** and etag-cached, then searched/filtered in JS. At this size the full
server-side rewrite (new params + consolidating two UI surfaces) is churn for no
meaningful payoff — decided (with the user) to **skip** it and revisit only if the
channel list grows large. `GET /data/channels` stays the documented bounded-exception
in `docs/unbounded-query-audit.md`.

## 10. Phase 5 — Move AI prompt assembly server-side

### T5.1 — Backend assembles prompts

**Current state.** `frontend/src/lib/posts/post-view.ts:197::formatPostsForPrompt` concatenates
every post into one string, passed as `postsText` to `api.summaryStream` / `chatStream` /
`summaryPrompt` / `tagStream` (`frontend/src/services/ai.ts:37,56,84,151,237,251`).

twice, bulkier the second time, with no token budget anywhere.**

**Fix.** Change these endpoints to accept `{channels, startDate, endDate, filters}` and assemble
the prompt on the backend from its own DB, reusing the existing templates in
`backend/app/prompts/templates.py`. Add an explicit **token/post budget** with deterministic
truncation. Port the filter semantics currently in `buildFilteredPostsFromRaw`
(keyword / forwarded / media / per-channel cap) into query parameters.

**Special case — `AIContext.tsx:387` `completePendingSummary`:** it fetches a full date range
only to regex-match ~10-20 cited post IDs. Switch it to the T2.2 bulk lookup; it does not need
the summarize path at all.

**Preserve `AIContext.tsx:460` `generateBackgroundSummary`** — it genuinely needs its post set.

**⚠️ Output parity is the acceptance criterion.** The assembled prompt must be **byte-identical**
to what the frontend produced for the same inputs, or summaries will silently change quality.
Write a parity test comparing backend assembly against the existing
`formatPostsForPrompt` output for a fixed fixture **before** changing behaviour.

**Verify.** Parity test above; backend tests for budget/truncation; then generate a real summary
