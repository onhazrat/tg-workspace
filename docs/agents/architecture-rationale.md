# Architecture rationale (archive)

Every invariant in `CLAUDE.md` is stated there as a claim plus a pointer to the
test or module that enforces it. This file is where the **argument** for those
claims lives when it is not already in a docstring.

Read the enforcing test first. Most of these arguments exist in a longer and
better-organised form in the module or test docstring `CLAUDE.md` points at —
`app/services/tenancy.py` and `tests/services/test_tenancy_seam.py` are the
reference examples, and both open with the same reasoning at more length. This
file is the safety net for the parts that live nowhere else, and the record of
what each ticket concluded.

Text below is preserved verbatim from `CLAUDE.md` as of 2026-09-02, when the
root file was cut from 151 KB to a claim-and-pointer index. It is a snapshot:
when an invariant changes, the authority is the enforcing test, then
`CLAUDE.md`, then this file.

Ticket-by-ticket narrative — what was tried, what review caught, what the
obvious implementation would have got wrong — belongs in `docs/*-plan.md` and
`docs/multi-user-tenancy-tickets.md`, not here.

## Backend architecture

- **Three model modules, split by what the models *are*.** `app/models.py` holds the template auth models (`User`, `Item`). All TG domain models — channels, posts, summaries, bot credentials, embeddings, logs, sync metadata, and `AppSetting` (JSON settings rows) — live in `app/models_tg.py`. `app/models_rbac.py` holds `Role` and `UserRole`. Alembic's `env.py` imports all three; a model module it does not import is invisible to autogenerate, which silently produces an empty migration rather than an error. The split is **by category, not by count**: RBAC is neither template auth nor TG domain, and filing it under the nearer wrong heading would have made that module's stated purpose false. A fourth category gets a fourth module; a model that fits an existing one does not.
- **Authorisation names a permission, never a role.** *Enforced: `tests/api/test_permission_checks.py`.* `app/core/permissions.py` holds the `Permission` constants and the three seeded roles; `app/services/rbac.py` (read model) resolves a User's permissions from `rbac_user_roles`; routes gate on `Depends(require_permission(Permission.X))`. **Nothing reads `is_superuser` to decide access** — the column survives until a later ticket drops it, but two answers to "can this user do X" is drift that fails closed, so the guard forbids it. Permissions are code because they are a closed set the code names; roles are data so a fourth role is an `INSERT`. `reconcile_seeded_roles` runs on every boot because migration seeds and code constants otherwise diverge the moment someone adds a permission — the row would still hold yesterday's list, and the row is what authorisation reads. It touches **only** the three seeded ids; a role an operator added is theirs.
- **A View-as session is a token whose subject is somebody else.** *Enforced: `tests/api/test_view_as.py`.* Ticket 26. `POST /view-as/{user_id}` exchanges an Owner's token for a short-lived one whose `sub` is the **target account** and whose `act` claim is the acting Owner. Putting the target in the standard claim is the design rather than a shortcut: the tenancy seam, the follow scoping, every by-id read and the browser's storage namespace already answer for `sub`, so "looks at the app exactly as that User sees it" becomes true of the ~40 read paths nobody would have remembered to audit. The alternative — Owner in `sub`, target alongside — is the change that is 95% done for a year. It also settles the ribbon: the spec's decision is that it is driven by a claim, so it survives a reload with no state, no request and nothing to rehydrate, which is why both email addresses ride in the token.
  - **The refusal lives in `get_current_user` and nowhere else.** Every authenticated route resolves its caller there, so one gate covers all of them; a middleware would be a second gate to keep in step, which is the drift that left `/password-recovery` unreachable for months, and a per-router dependency is the rule somebody forgets on the ninety-first route. What it refuses is **any non-safe method, minus a declared read-only allowlist** — five routes here are reads expressed as POST purely so the channel selection travels in the body, and every one says so in its own docstring; refusing them would leave a View-as session unable to open the Posts tab, which is the screen a reported problem is usually about. `VIEW_AS_READ_ONLY_PATHS` is an **inventory**, not a set of special cases: the guard walks every mutating operation the app mounts and fails on one that is neither refused nor named there with a reason, then calls each allowlisted path with a real token so an entry nothing exercises cannot pass as a rule. `POST /rag/search` is deliberately not on it — it calls an embedding provider, which costs money and writes a log.
  - **A third bucket exists and had to be derived.** Four mutating routes authenticate nobody — sign-in, signup, reset-password, password-recovery — so the gate structurally cannot reach them, and a View-as token sent to one is an ignored header. That is not a hole (none of them touches the viewed account), but it is a fact the guard computes from the dependency tree rather than remembering, reusing `test_public_route_exemptions.py`'s own `_requires_auth` so the two cannot come to disagree about what "authenticated" means.
  - **The browser layers the token; it never replaces it.** `access_token` stays the Owner's and `view_as_token` sits on top, preferred by `headers()` through `activeToken()`. Exiting is one `removeItem` and so is a target that vanished, which is what makes the last checkbox — "returns the Owner to their own account" — true rather than approximate. A design that overwrote the Owner's token can only restore it, and a restore can fail. `VIEW_AS_TOKEN_STORAGE_KEY` is therefore the **third** device-scoped key, argued for rather than merged in passing: namespacing a token by the account named inside it is `access_token`'s own circularity one level up. The storage namespace does follow the *active* token, so preferences are read under the account being viewed.
  - **A deleted or disabled target gets its own detail string, and that is the whole of the checkbox.** `api/base.ts::isAuthFailure` treats 404 `"User not found"` and 403 `"Inactive user"` as a dead session and hard-navigates to `/login` — answering either here would sign the **Owner** out over something that happened to somebody else's account. So `VIEW_AS_ENDED_DETAILS` is a pair of distinct strings, asserted as an exact set on both sides of the wire, and the transport drops the View-as token instead of the session.
  - **The audit row does not cascade, alone in this schema.** Every other per-User table takes `ondelete="CASCADE"` from `user.id`; `view_as_sessions` takes `SET NULL` on both keys and denormalises both addresses, because the case a reader most wants an answer for is the deleted account — which is the ticket's own last checkbox. It lives in a **fourth model module** for `models_rbac.py`'s reason: a record of an administrative act is neither template auth, nor TG domain, nor roles, and filing it under the nearest heading would make that module's stated purpose false. Nothing revokes: a session *is* its token, nothing is consulted while one is in use, and a revocation list would be a second authority disagreeing with `exp` over a thirty-minute window. Disabling the account is the early stop, and it already answers.
  - **The bootstrap superuser is an Owner now.** `VIEW_AS` is held by the `owner` role alone, and `init_db` granted `admin` — so without this the ticket ships as code no deployment can reach. Owner is a strict superset of Admin today, the migration promotes existing superusers exactly as ticket 07's did, and `test_rbac.py` now asserts the **permissions** the bootstrap account holds rather than its role id: a test naming the role would have failed on a change that took nothing away, which is the brittleness roles-as-data exists to avoid.
  - **Review found the two failures that were not on any checkbox.** The first: the ribbon was mounted in `routes/_layout.tsx`, which does not wrap `/summarizer` — that lives under `_tg`, a branch whose component is a bare `Outlet` — so it was absent from the one screen an Owner reproducing a problem actually spends the session on. It is at the **router root** now, because a View-as session is a property of the browser and not of a route subtree, and `--view-as-offset` is what stops the row it takes pushing the summarizer's last 40px off a `h-svh overflow-hidden` layout. The second was a **loop**: `activeToken()` returned the stored token whatever its `exp`, so past expiry the ribbon was already gone while every request still carried the dead token, the server answered 401 `"Could not validate credentials"` — not one of `VIEW_AS_ENDED_DETAILS` — and the transport cleared the *Owner's* token while leaving the View-as one in place, which the next sign-in then preferred again. Expiry is the ordinary way a session ends, so it now falls back to the Owner's token exactly as exiting does, and `clearStaleSession` takes both layers. Neither is reachable from the seven checkboxes; both are guarded now.
  - **Ticket 27 owns elevation**, and one thing here is shaped for it: `mode` is a string on both the token and the row rather than a boolean, because a second answer to "what may this session do" would otherwise be a second field, and two fields that must agree eventually do not. `routes/view_as.py` deliberately carries **no** nesting check — the exchange is a POST and the read-only gate already refuses it, so a branch there could not fail — and the requirement lives in the guard instead, where it will still be asserted on the day an elevated session can POST.
- **Row visibility has one seam, and it is on.** *Enforced: `tests/services/test_tenancy_seam.py`, `tests/api/test_account_isolation.py`.* `app/services/tenancy.py` answers "which rows may this User see"; `TENANCY_ENFORCED` ships **`True`** since ticket 21 PR 4, so `scoped_select` filters: a user-owned row by its owner, a follow-scoped one by an `EXISTS` against `tg_channel_follows`, and corpus not at all. It shipped `False` for eighteen tickets, which is what let the ~40 read paths that never had an owner filter adopt the seam one batch at a time without any batch changing a response. **Off is now the rollback**, and a real one — the disabled branch is still asserted byte-identical to the pre-seam queries for all 27 models, so `TENANCY_ENFORCED=false` in `.env` reverts every read path at once with no deploy of different code. What it costs is stated once, in `test_account_isolation.py::test_turning_the_flag_off_reopens_cross_account_reads`: pre-seam means every account sees every account's rows. It is for an emergency, not a preference. The flag is read in **exactly one function**, `tenancy_enforced()`, and a guard greps the whole of `app/` to keep it that way: the failure mode of a flag is always the fourteenth place it got read, which is the same shape as the two auth gates that disagreed about `/password-recovery` for months.
  - **Dispatch is by model class, because `.where(Model.user_id == user_id)` is wrong for most of the schema.** The corpus is already physically shared — `Channel.id` is the handle, `Post` is unique per `(channel_name, post_id)` — so `user_id` on those tables is a "who scraped this first" stamp, and filtering on it would hand the second follower of a channel an empty page for posts sitting right there. Those are **follow-scoped** (an `EXISTS` against `tg_channel_follows`, built in ticket 04) and their `user_id` columns were dropped in ticket 22. The EXISTS correlates on `FOLLOW_KEYS`, not on a guessed column name: `Channel` spells the join key `id` and the four corpus tables repeat it as `channel_name`, so one hard-coded name would scope four of the five against the wrong column **and still compile**. `DiscoverHandleProbe` and `SyncMeta` are **corpus**: shared and unreachable through a follow, unscoped on purpose, because an unscoped read is otherwise indistinguishable from a forgotten one. The remaining 18 tables are **user-owned**.
  - **A 404 is only half an answer; the body is the other half.** `assert_owner` refuses a foreign row as 404 rather than 403 — 403 confirms the row exists, which is the enumeration oracle signup was hardened against — but every 404 here names its resource (`"Summary not found"`, `f"{log_type} log not found"`), so a generic `"Not found"` would move that oracle into the payload instead of closing it. `detail` is a **required** keyword argument with no default, because the default is the trap. `unscoped_select(statement, reason=...)` is the matching escape hatch for reads that cross accounts on purpose (Admin export, `routes/data/admin.py`): a no-op by construction whose only job is to make the call site greppable and the reason written.
  - **Scoping a read means finding every read it makes, not the one it is named after.** *Enforced: `tests/services/test_post_tenancy_scoping.py`.* Ticket 16 moved the feed, lookup, counts and Discover onto the seam, and the Post select was the easy half. Two things were not. `list_feed` has **two query shapes**: with a per-channel cap it wraps the base select in a `row_number()` subquery, so the predicate has to go *inside* that subquery or the window ranks rows the caller cannot see and the cap is computed over the wrong set. And all three modules carried their own copy of `select(Channel.name)` to answer "do I follow this handle?" — the `unfollowed_forwarded` filter and Discover's `isFollowed` flag — which unscoped reports a candidate as followed because *somebody else* follows it. That is now `follows.visible_channel_names`, named for what it returns while the flag is off (every Channel) rather than what it returns once it flips. Review found a **fourth** copy the first cut missed, in `discover_reports.followed_names` — the one that runs *after* the aggregation and overwrites its scoped answer, so a saved report and a live one would have disagreed about `isFollowed` for identical input. Scoping the read a function is named for is the easy half; the ones that matter are the reads it makes on the way to returning.
  - **An Artifact is private, and a writable row is half the question.** *Enforced: `tests/services/test_artifact_tenancy_scoping.py`.* Summaries, chats, tag runs and Discover reports (ticket 17) are all `USER_OWNED` — an artifact is what an account *produced* over a scope, never a copy of the corpus it read, so none of the four is follow-scoped. Each family's list goes through `scoped_select` and each by-id call through `assert_owner` with **the detail string that family already answers for an absent row** (`"report not found"` stays lower-case; matching the existing string is the requirement, tidying it re-opens the oracle). The **writes are in scope too**, which the ticket's own checkboxes did not say: `upsert_*` merges into whatever row its id names, so a scoped read over a writable row lets a second account overwrite the first's summary by guessing an id — and every read guard passes throughout. An absent id still creates.
    - **The unified History gave up its own owner filter.** `/data/artifacts` hand-rolled `owner == me OR owner IS NULL` before ticket 17, written pre-emptively while nothing else scoped. Two owner filters with different NULL handling is the drift `tenancy.py` exists to prevent, and it would surface as a row visible in History and absent from `/data/summaries`. It is the one adoption that **changed a response while the flag is off** — deliberately, and confirmed before implementing, because a single-operator deployment has one account and the alternative leaves a fifth NULL rule for ticket 21 to reconcile. The predicate goes on **each leg, not the union**, because there is nowhere else to put it — the union is wrapped in a subquery projecting the labelled output columns and `user_id` is not among them, so the outside has nothing to name.
    - **`report_to_camel` answers for the viewer, never the owner.** Ticket 16 had to pass `viewer_id=report.user_id` as a commented placeholder because `get_report` had no authenticated viewer; ticket 17 gives it one and drops `followed_names`' `user_id=None` branch with it. The argument keeps its own name although the two values coincide once reads are scoped — the day a report becomes shareable they stop being the same question, and a call site spelling it `report.user_id` would answer the wrong one without changing.
  - **A dismissal is one account's judgement, and the owner is half the key.** *Enforced: `tests/services/test_discover_dismissals_are_per_account.py`.* `tg_discover_ignored` was keyed by `handle` alone (ticket 30), so the first account to dismiss a candidate dismissed it for everybody. **Scoping the read without moving the key is worse than leaving the table alone**: `ignore_channels` skips a handle that already has a row, so once A dismisses `@foo`, B's write is a no-op *and* a scoped read then tells B the handle is not dismissed — B can never dismiss it and the button silently does nothing, a functional regression rather than a visibility one. So the key, the reads and the writes moved together: composite PK `(handle, user_id)`, a real cascading FK, and existing rows adopted by `resolve_follow_owner`'s rule.
    - **This is the one family whose owner filter is *not* `scoped_select`.** The seam's filter is gated on the flag because it answers *visibility*; the owner here is part of the primary key, so filtering on it answers *identity* — which row is yours — and a flag cannot gate identity. Gated off, both accounts collide on one row again and the composite key is decoration. Every guard is therefore parametrised over both flag states, and the mutation that gates the filter fails **only** the flag-off variants: that asymmetry is the signature of the half-fix the ticket refuses.
    - **The migration settles owners rather than deferring them.** A composite primary key cannot hold NULL, so "belongs to nobody" stops being expressible the moment it runs. NULL and an id left behind by a deleted account get the same answer — the operator — because they are the same situation; a live owner is kept. A database with **no account at all** drops its rows rather than leaving them unkeyable, which is safe in the only way it can happen (that table is empty before the first superuser exists, and every read now requires a caller). It completes in one pass: alembic stamps a revision and never re-runs it, so a migration leaving work "for the next deploy" leaves it undone for ever — ticket 06's migration claims otherwise in its own docstring and that claim is wrong.
  - **A sync log is telemetry about a Channel, so it carries no owner at all.** *Enforced: `tests/services/test_sync_log_channel_telemetry.py`.* Ticket 19 moves `SyncLog` and `SyncLogPayload` to `FOLLOW_SCOPED`: the row answers "did this Channel deliver Posts, and if not why not", and the second follower of a handle has as much right to that as the first. `upsert_sync_log` **took** a `user_id` it deliberately did not write, because `data_import_export._LOG_IMPORTERS` dispatched all five log types through one uniform signature; **ticket 22 dropped the column and the parameter together**, and the two dispatch tables now name that asymmetry in a visible branch — an ignored parameter decays into a written one the first time somebody tidies it. The payload table gains a denormalised `channel_name` for the same reason it already denormalises `timestamp`: the seam correlates on a real column, and reaching the parent's name through a join would put `tg_sync_logs` inside the predicate of every read of the table the payload split exists to keep cheap. **`assert_owner` on an ownerless row does not degrade, it fails closed** — `owner_id is None` raises — so ticket 18's write-takeover guard had to be restated as a Follow check rather than deleted, and it checks both the Channel the incoming log names and the one an existing row at that id already names. Deleting one row of a type nobody owns is now an administrative act (`SHARED_LOG_TYPES`, derived from `SCOPES`, never listed), which also closes the network-log hole ticket 18 left: their *reads* went Admin-only while any authenticated account could still delete one by id.
  - **An import is a door onto the same tables, and it had no lock at all.** *Enforced: `tests/services/test_import_write_scoping.py`.* Ticket 17's own argument is that a scoped read over a writable row is half a fix; it closed that for the four artifact families' endpoints and not for `POST /data/import`, which reaches Summary, BotCredential, ChatDestination and the logs through a bare `session.get(Model, id)` and an overwrite (ticket 31). The credential case rewrote another account's **token**, and because every log `upsert_*` assigns `user_id` on its existing branch too, the clobber was a takeover rather than only a rewrite. `POST /data/bot-credentials/migrate` is the same import by another name — bulk, merged by id, carrying tokens, and not even Admin-gated — so it is covered by the same rule; fixing one door and leaving the other is the mistake the ticket exists to correct.
    - **Import is per-account, because it cannot express anything else.** The ticket offered a second design — let an Admin write across accounts, since a restore that cannot restore is not a restore — and the reason for refusing it is narrower than a preference: every importer stamps a new row with the *caller's* id and an export document carries no owner at all, so a restore into an empty database already files every account's rows under whoever ran it. Refusing to overwrite a foreign *existing* row takes away nothing that worked, and needs no new permission constant. Ticket 28 is where export and import learn to carry a subject; `test_import_stamps_new_rows_with_the_caller_not_the_document` fails the moment they do, so that ticket has to re-take the decision instead of inheriting it. The route's `DATA_ADMIN` gate is not this answer — it decides who may call import, never whose rows the call lands on.
    - **A read may be gated; a write may not.** *Enforced: `test_import_write_scoping.py::test_only_reads_use_the_gated_ownership_guard`.* `assert_owner` defers to the flag, `assert_owner_on_write` does not, and which one a call site takes is the difference between a rule that holds now and one that waits for ticket 21. Ticket 31's first cut built the ungated guard for the import door and left **nine** by-id writes on the gated one — `PUT /data/summaries/{id}`, `POST /data/logs/{type}` and `PUT /data/bot-credentials/{id}` among them, all plain `CurrentUser` with no permission gate, all still rewriting another account's row on the shipping config. Review caught it. The guard now names the six functions allowed to call the gated primitive, all reads, each with a reason; anything else calling it fails. Refusing to *show* a row is a visibility change and that is exactly what the flag defers, so the reads stay gated on purpose.
    - **A flag's default lives in two files, and the suite can only see one of them.** *Enforced: `tests/deployment/test_env_example_matches_defaults.py`.* Ticket 21 PR 4 moved `TENANCY_ENFORCED` to `True` in `config.py` and left `.env.example` shipping `false`. That file documents every tunable and is what a root `.env` is built from, so a fresh install would have run **unenforced with the whole suite green** — the flip shipped and did not ship at the same time, depending on how a deployment got its `.env`. This is not a check that broke; it is a class the suite **structurally cannot** catch. `test_the_flag_ships_on` reads `model_fields[...].default` rather than the resolved setting, deliberately, because the suite is run in both flag states and asserting the resolved value would fail the rollback rehearsal; every probe in `test_account_isolation.py` pins the flag on for the same reason. So the resolved configuration was unasserted in **both** directions and the one file that decides it for a real deployment sat outside the tests entirely. The guard compares **booleans only**: a general key-match drowns in placeholders and hostnames, while a boolean is a switch whose two values are both valid configurations, so a mismatch looks wrong nowhere — the same shape as the flag it was written for. A deliberate divergence goes in `SKIP` with its reason.
    - **A check can stop applying because its input got *better*.** *Enforced: `tests/api/test_admin_route_gating.py`, `tests/api/test_account_isolation.py`.* Every other finding in the tenancy programme was a missing check; this one was a check that went dead when the data model improved, in the same commit. `POST /jobs/sync/{id}/cancel` shared `_visible_job` with the two read routes, and that was safe only because a sync job used to be the caller's or **nobody's** — the scheduler's carried a NULL owner, so a job that was not yours hit the `JOBS_MANAGE` branch and was refused whatever the flag said. Ticket 21 PR 1 gave scheduler jobs a real owner, and a foreign job then fell through to the flag-gated `assert_owner` alone, which on the shipping config is a no-op: any signed-in account could stop any other's in-flight sync by guessing an id. The fix is `_cancellable_job`, the same three cases on the ungated primitive, and the structural guard now names **which** of the two each handler must call rather than accepting either. The identical shape was found again on the three bulk-follow routes, which took `_current_user` and never used it — and there the cancel resolved the job, cancelled it, and *then* answered 404, so the refusal arrived after the damage. When a nullable column gains a real value, re-read every branch that was reachable only because it was null.
    - **`assert_owner_on_write` is the seam's one non-inert function.** Ticket 30's rule, reached from the other side: overwriting a row that is already somebody else's is not a read, so refusing it changes no response on a single-account deployment, while gating it would leave the clobber open on exactly the deployment that has a second account. A flag cannot gate identity. The one flag-dependent half is **NULL**: an unstamped row stays writable while the flag is off, because legacy rows and anything a background job wrote carry no owner and refusing them would fail closed against the only account a single-operator install has. Under enforcement that flips, and an import is one transaction — so after ticket 21 the *first* ownerless row aborts a whole restore, which is why ticket 31's file asks 21 for an owner backfill rather than letting a write silently adopt the row.
    - **The two credential families had no owner check at all** — not a gated one, none — on `upsert_`/`delete_bot_credential` and the same pair for chat destinations, behind routes any signed-in account can reach. `PUT /data/bot-credentials/{id}` naming a foreign id replaced that account's stored **bot token**. Closed by ticket 31 with the rest. Deferring them was the first cut's mistake, on the reasoning that scoping a write without its read is the half-fix ticket 17 names — but that ticket's half-fix was scoping a *read* and leaving the write, which is the opposite direction. The write is identity and ungated, the read is visibility and gated; they are separable, and only one of them lets a stranger replace a token. **The matching reads** are closed by ticket 31's own review finding, as ticket 32 — see below.
  - **A read adopts the seam; it does not hand-roll the filter.** *Enforced: `tests/services/test_credential_tenancy_scoping.py`.* `list_bot_credentials` and `list_chat_destinations` were a bare `select(Model)` with no `user_id` parameter at all (ticket 32), so both list endpoints returned every account's rows. **What leaked was the id, not the token** — `bot_to_camel` returns `hasToken` and never `token_encrypted` — and the id is the part that matters, because `jobs/auto_summary.py::_auto_publish` resolves `publishBotId` and `publishChatId` by id with **no owner check at all**, while `routes/telegram.py::_resolve_bot_token` makes exactly that check on the interactive path. Scoping the list takes another account's credential ids out of the UI; it does not take them out of reach. That door is ticket 33, below.
    - **The scheduler sent as whichever bot the Summary named.** *Enforced: `tests/services/test_auto_publish_scoping.py`.* Ticket 33. `upsert_summary` passes unknown body keys straight into `Summary.extra`, and credential ids are **client-chosen strings** taken from the path of `PUT /data/bot-credentials/{bot_id}` — guessable, not random. So a Summary could name another account's `publishBotId` and `publishChatId`, and the scheduler would decrypt that account's token and send as its bot to a destination that account chose. The check goes in **`publish_summary_text`**, not only in `_auto_publish`: that is the function that decrypts, and guarding the caller leaves the next caller unguarded — the `/password-recovery` shape, and ticket 31's nine by-id writes. It refuses *before* `decrypt_token`, because a refusal that arrives after the plaintext exists has already produced the thing the encryption is for. `acting_user_id` is a **required keyword with no default**, ticket 32's lesson: an optional actor leaves every existing call site passing nothing and still passing its tests. The exploit is **latent rather than live** on the shipping config, because `run_auto_summary` still selects `Summary.user_id == operator OR IS NULL` — that filter goes away with the operator model, and this is a token decryption reached by a guessable id, so it closes now.
      - **A refusal writes a failed publish log; it does not return quietly.** The scheduler is unattended, so a silent `return` makes "auto-publish is misconfigured" and "auto-publish is off" the same observation. An **absent** destination used to do exactly that, so absent and foreign now answer alike, with the same text — `assert_owner`'s rule that the body is the other half of the answer, applied where there is no status line at all to carry it.
      - **`may_act_on` is `assert_owner_on_write` without the raise**, and both callers here are in the scheduler with no response to put a 404 in. Stating the rule once is the point: two spellings of "is this row mine" is the drift the seam exists to prevent, and they diverge on the NULL branch first. A NULL on **either** side — the row's owner or the actor's — is unanswerable, so it is permitted while the flag is off and refused under enforcement. The actor half is not hypothetical: `run_auto_summary` deliberately picks up ownerless Summaries. This is the opposite of what ticket 32 did to the credential *lists*, and deliberately so — handing every account the deployment's stored credential is a leak, declining to use one is not. It is another line on **ticket 21's owner-backfill bill**.
      - **The interactive twin was the divergent one, and review caught it.** The ticket cites `routes/telegram.py::_resolve_bot_token` as the reference implementation — but it hand-rolled the rule, and consolidating the scheduler's copy while leaving the twin spelling it differently is the half-fix this repo names. It answered **403 `"Bot credential not accessible"`** for a foreign row against 404 `"Bot credential not found"` for an absent one, over client-chosen ids: an enumeration oracle any signed-in account could walk, on a live route. And it refused only a *stamped* foreign row, so under enforcement that door would publish with an unstamped credential the scheduler refuses. Both now take `may_act_on` and answer 404 with the family's own string. The 403 is not a lost response: on a single-account deployment there is no foreign row to refuse, and `isAuthFailure` never keyed on that detail.

Sequenced plan: `docs/scaling-to-multiple-workers.md` (steps 1 and 4 done, 3 is ticket 13). **Scale the API tier, never the sync tier.**
  - **Every sync mode enqueues, one message per Channel** (decision 30). `app/jobs/sync_queue.py` is the consumer for all six lanes (`sync_lanes.DRAIN_ORDER`); `POST /jobs/sync`, `run_auto_sync` and bulk follow all call `enqueue_sync_job`. A message is one Channel so it can be attributed, timed out and failed on its own; the batch lives on in the job row, and **the last Channel to finish is what makes the job terminal** (`_finalize_if_complete`) now that no `run_sync_job` sits above them. An enqueue **rings the worker over `NOTIFY`** rather than draining locally, and the 30s sweep is the backstop for a lost ring.
  - **Six lanes, and the drain is weighted rather than ordered.** *Enforced: `tests/services/test_lane_draining.py`, `tests/services/test_sync_lanes.py`.* Ticket 12 completes decision 27's product — `{auto_sync, manual_bulk, manual_single} x {normal, best_effort}` — and `services/sync_lanes.py` holds both the names and the policy, as a **pure transform**, so the fairness property is testable without a queue behind it. `LaneScheduler` is strict between tiers and weighted 3:2:1 within one, favouring single, then bulk, then automatic. **Strict order within a tier is the obvious implementation and is the failure decision 29 names**: a steady trickle of single syncs never empties, so auto-sync never runs and the deployment quietly stops updating while the worker looks busy. The weighting is smooth (nginx's smooth WRR) rather than "three, then two, then one", because the picks are separated by however long a real sync takes and a burst of one Budget is the thing being prevented. Credit only moves for lanes that had work at that moment, so an idle lane cannot bank a burst. The three best-effort lanes exist with **nothing enqueueing onto them** — ticket 23 selects a tier — which is not a mechanism with no caller: the consumer is the caller, and `pgmq.read` raises on a queue that was never created.
    - **A slot is filled the moment it frees, and that resolved both inherited head-of-line notes.** Ticket 10 read a batch per lane and awaited it as a unit, so one Channel in a deep backfill held its slot until its batch finished and no other lane was read until that lane drained; ticket 11 left a coalesced waiter holding a concurrency permit while it waited, so N requests for one busy Channel occupied N scraping slots to scrape nothing. Both are the same object, so one change closes both: `drain_sync_lanes` takes a permit, dispatches **one** message, and comes back, and the permit is a `SyncSlot` the waiter can put down (`slot.released()`) and re-take before its next claim attempt. **It still cannot deadlock** — ticket 11's argument was "the holder takes its permit before it can claim", and that half is untouched: a claim holder never releases while it walks, and only a waiter releases, so no permit is held by something waiting for a claim held by something waiting for a permit. `COALESCE_MAX_WAIT_SECONDS` keeps its value and **loses its original reason**: the gate justification is gone, and what remains is that the waiter's message is claimed under a ~2.4h visibility timeout it must not outlast, and that a person is on the SSE stream.
    - **"Interleaved across Users" is done at the read, not at the enqueue.** *Enforced: `test_lane_draining.py::test_one_accounts_backlog_does_not_block_another_accounts_work`.* A deliberate departure from decision 31's wording that honours its stated reason. Every enqueue call carries exactly one account (`enqueue_sync_job(job, user_id)`), so interleaving there can only reorder within one call — and the failure the decision names is "a user following 500 channels would otherwise block everyone behind them", which is *across* calls. PGMQ is FIFO by `msg_id`, so the two only meet at the read. `_read_interleaved` issues one `pgmq.read` per account with due work, using PGMQ's own `conditional` filter, and merges round-robin; below two accounts it does not engage at all. **Not `pgmq.read_grouped_rr`**, which exists and looks like exactly this: it only reads from groups whose *head* message is visible, so claiming one of an account's messages makes the rest unreadable until it is archived — one sync at a time per account.
    - **An Admin can pause or drain one lane** (`services/sync_lane_control.py`, an orchestrator). **Pause** stops the worker reading that lane and is lossless — the messages stay queued *and visible*, so a resume waits out no timeout. **Drain** means purge: archive everything on the lane, then `cancel_job` every job those messages belonged to. Cancelling is not tidiness — since ticket 10 a job is terminal only when its last Channel finishes, so archiving 40 of a 50-message batch would otherwise leave the job non-terminal for ever and `has_active_sync_job()` answering True, which makes auto-sync skip every tick from then on. Drain deliberately does **not** mean "run this lane now": the enqueue ring plus the 30s sweep already are that. Gated on `Permission.JOBS_MANAGE` rather than a new constant, which already covers enabling a job and already admits to being destructive.
  - **One sync per Channel at a time, and the claim is a row.** *Enforced: `tests/services/test_channel_mutual_exclusion.py`.* Ticket 11. Two backward walks of one Channel interleave their writes to `last_updated`, `anchor_post_id`, `oldest_stored_post_timestamp` and `history_complete_to_cutoff`, and the row that results describes neither walk. Posts are safe without any of this — `bulk_upsert_posts_impl` upserts on the unique constraint — those four are not. The protection was `scraper_jobs._channel_locks`, an `asyncio.Lock` that stopped meaning anything the moment the scheduler left the web process; it is now `Channel.sync_claimed_at` / `sync_claimed_by`, taken by a conditional `UPDATE ... RETURNING` in `services/channels.py`. The lock is **deleted, not kept beside it**: two answers to "is this Channel being synced" diverge the moment the second worker arrives, and which one a call site consulted decides whether the cursors were protected. The claim lives in `sync_single_channel` rather than in its two callers, for ticket 33's reason — that is the function that walks the pages, and guarding a caller leaves the next caller unguarded.
    - **The lease is not the visibility timeout, and the difference is the point.** Five minutes against the VT's ~2.4 hours. The VT decides when a crashed worker's *message* comes back; the lease decides when its *Channel* does. Sizing one off the other leaves a Channel that died at noon refusing every sync until 14:24, including one a person is sitting in front of. A live sync renews on a heartbeat at a third of the lease, so the lease bounds how long a **dead** holder blocks the Channel and never how long a live one may legitimately take — a deep backfill is in no danger of having its claim stolen mid-walk. And because an expired claim is simply taken by the next caller, "a crashed worker's Channel is picked up again" needs no reaper, no sweep and nothing for an operator to run.
    - **Release and renew are conditional on the holder; that is not tidiness.** A runner that overran its lease and had the Channel taken from it still reaches its own `finally`. An unconditional release there clears the **new** holder's claim and hands a third walk into cursors the second is mid-write — the same interleaving, arrived at through the cleanup path instead of the claim path.
    - **The second request rides the first and is not charged.** `_claim_or_coalesce` waits on a `channel_sync_release` notification, with a poll of the claim as the backstop a `NOTIFY` always needs (no replay). It re-attempts the claim every pass, which is both the lost-wakeup fix and the crashed-holder takeover. "Not charged" needed no new code — a coalesced request never enters the walk, so its meter counts nothing and a charge of zero writes no row — but **both halves are asserted**, because either alone passes for a request that scraped and was let off. A lost ring reports the outcome from the row rather than re-claiming: re-claiming there would scrape a Channel that was just scraped, which is the double work coalescing exists to prevent, reached through the one path where nobody is watching.
    - **A waiter holds a concurrency-gate permit while it waits.** Stated rather than glossed: it cannot deadlock, because the holder took its own permit before it could claim, but N requests for one busy Channel occupy N slots. So the wait is capped (`COALESCE_MAX_WAIT_SECONDS`, 15 minutes) and reports a **skip** past it — nothing went wrong, and the Channel is demonstrably being synced. Draining as slots free belongs with ticket 12, which owns the draining strategy; this is the head-of-line shape `sync_queue._batch_size` already documents.
    - **The claim is not the deadline** (decision 33). `next_regular_sync_at` / `next_dynamic_sync_at` are advanced only by `_finalize_channel_success`. Advancing a deadline at claim or enqueue time conflates "enqueued" with "synced", and strands a Channel silently the moment a message exhausts `read_ct` and is archived: the schedule says it ran, and nothing did. Neither claim column is indexed and neither touches `updated_at` or `touch_sync` — every access is by primary key, and bumping the channel-list etag three times per sync for a field the list does not render is churn on the table every page read touches.
  - **One worker per proxy, and the worker count derives from the proxies.** *Enforced: `tests/services/test_proxy_worker_partition.py`.* Ticket 13. The consumer held one `asyncio.Semaphore` sized `min(syncConcurrency, total lane slots)`, which said how many Channels could be walked at once and **nothing about which proxy any of them used** — so a Channel's backward walk hopped proxies page by page and a burst of syncs piled onto whichever lane was least loaded at that instant. It is now a partition (`proxy_pool.build_workers`): one worker per lane slot, pinned to its lane for the whole message, dealt **round-robin across lanes** so that `syncConcurrency` below capacity spreads over distinct proxies instead of stacking three workers on the first one. With no proxies configured the partition is `syncConcurrency` direct workers, which is byte-for-byte the old behaviour.
    - **The worker owns the lane; it does not hold the lane's permit.** What it holds for the whole message is the lane's long-lived `httpx.AsyncClient`. The semaphore permit is still per request, because holding it across a five-minute backfill would park every *other* kind of proxied traffic behind it — thumbnails, bot publishes, probes — and `ProxyPoolManager.acquire` starts raising `ProxyPoolExhausted` at 120s. `hold()` carries that same 120s bound turned around: one bound page fetch queues behind ~20 thumbnails of its own, so unbounded it would stall a message toward its 2.4-hour visibility timeout with nothing in the log. **`sync_queue`'s docstring claims this ticket makes `auto_summary`'s separate semaphore stop mattering, and that is wrong in both halves** — the per-proxy *rate* was never at risk there, since every proxied `fetch_with_retry` has always taken a lane permit; and its *channel* concurrency is still outside the partition, because it calls `run_sync_job` directly and giving it a worker means enqueueing, which inverts its control flow. The forward reference is still open.
    - **A bound worker does not hop, including on retry.** The fallback is the thing a reader will add back, so: hopping moves a dead proxy's load onto the healthy ones at the exact moment Telegram is already pushing back, which is how one rate-limited egress becomes a rate-limited set. "Capacity honestly reflects available proxies" *requires* throughput to drop when a proxy dies. The Channel is not lost — it fails this pass and the next sweep hands it to a worker whose proxy works, because the dead one's worker is parked.
    - **The binding travels by `contextvars`, and it binds the slot rather than the worker.** `core/request_meter.py`'s reason for the first half: the value is set by the consumer and read by the HTTP client, with `sync_orchestrator` and `scraper` in between reading neither. The second half is a bug found while writing it — a coalesced waiter puts its worker down and may take a **different** one back, so a captured worker leaves the walk fetching through a proxy that now belongs to another message, with the partition believing each has its own.
    - **A parked worker must not look like a hung one.** Both transitions log with the capacity that remains, and a drain that finds every worker parked says so and returns rather than blocking — unbounded there means the 30s sweep (APScheduler, `max_instances=1`) skips every tick behind it, so syncing stops with nothing in error. Deliberately **not** a runtime-config field: cooldown lives in `network._bad_proxies`, which is process-local, so a `parked` flag served by the API could never be true. `effectiveProxyCapacity` and `allowedConcurrency` already carry the width.
    - **The pin survives, reshaped.** The partition is built from process-local state, so two replicas would each own every proxy. `test_worker_count.py` asserts the new shape *and* the surviving reason, in both directions — ticket 11's rule that an inverted assertion beats a deleted one.
  - **A status code is Telegram answering; it is not a proxy fault.** *Enforced: `tests/services/test_adaptive_proxy_wait.py`.* Ticket 14. `fetch_with_retry` armed the ten-minute cooldown on any `is_network` exception, and `httpx.HTTPStatusError` subclasses `httpx.HTTPError` — so **a 404 from one deleted channel put its proxy in cooldown**. That predates ticket 13; what ticket 13 changed is the consequence, because a cooldown now parks the bound worker, so on a single-proxy deployment one dead handle stopped dispatch for ten minutes. `services/proxy_pacing.py` (a **pure transform**, for `sync_lanes.py`'s reason) replaces the one predicate with seven named outcomes: only a `TRANSPORT_FAULT` arms cooldown on its own, a `REJECTION` (429/403/5xx) or `SOFT_BLOCK` widens the per-proxy wait, and an `ANSWERED_ERROR` (404, 410, 451) changes nothing at all. The retry predicate is deliberately **unchanged** — it also decides how many attempts a status code gets, which is ticket 08's charging contract, so narrowing it here would quietly re-price the quota ledger while fixing something else.
    - **The wait is the graduated response and cooldown is the top rung of the same ladder.** A 429 means this egress is rate limited; declaring the proxy dead for ten minutes is not proportionate, and on a single-proxy deployment it is indistinguishable from an outage. So a rejection widens (`max(PACE_STEP_MS, wait x 2)`, capped at `PACE_MAX_MS`) and only arms cooldown once the wait is **already** at the ceiling and there is no wider wait left to try. `should_arm_cooldown` reads the pace as it was *before* the failure was folded in, which is why `_record_pace_failure` returns the previous value rather than letting the caller re-read the dict — reading it after arms one rejection early, and the pace never gets a turn at its widest. A **soft block never reaches that rung**: a channel Telegram will not serve on the web view is soft-blocked for every egress equally, so parking a lane over it punishes the proxy for a property of the channel.
      - **Where there is no ladder, a rejection still parks the proxy, and `paced` is a required keyword.** Only web-view requests are paced, so a thumbnail, a publish or a probe never widens the wait and the ceiling is unreachable for it — which would leave a proxy answering 502 on every request in rotation for ever, a regression hiding inside the fix. For that traffic the only two answers are "do nothing" and "cooldown", and an HTTP proxy that has failed upstream commonly announces it with its own 5xx. The rule stays narrower than the one it replaces where that matters: a 404 is an `ANSWERED_ERROR` and parks nothing either way.
    - **Healthy is zero, and narrowing is gradual on purpose.** A deployment nobody is pushing back on sleeps for nothing and stores nothing — the cursor dict stays empty, which is the leak `_prune_expired_cooldowns` already had to fix once. `PACE_NARROW_AFTER_SUCCESSES` consecutive successes narrow the wait one step; snapping back on the first success re-provokes the limit that caused the widening, and the deployment then alternates between hammering Telegram and being refused by it. A floor snap is what makes it actually *reach* zero rather than decaying toward it for ever.
    - **Latency drift is a weak signal, and "weak" is two numbers.** Drift widens by `PACE_DRIFT_FACTOR` (1.25) against a rejection's 2.0, and never past `PACE_DRIFT_MAX_MS` (5s) against the full 30s ceiling — a proxy that is merely slow must not end up throttled as though it were refused. It needs `PACE_DRIFT_MIN_SAMPLES` behind the EMA first, because the first request through a cold lane is always slower than an average that does not exist. Drift is measured **before** the sample joins the EMA: folding first lets a spike drag the mean it is compared against, and does it more the larger the spike is.
    - **`latency` is the request, timed from just before it goes out.** Not from the top of the attempt, which is what it was and is wrong in two ways: it would include the deliberate sleep, and — the one that bites on a healthy deployment — the time spent queued for the lane permit. `hold()`'s docstring notes a page fetch routinely waits behind ~20 thumbnails at the default of one slot, so ordinary contention would read as a latency spike, trip `_is_drifting`, and throttle a proxy Telegram never pushed back on. The pace feeds on this number; it must measure only what Telegram did. The guard for the sleep half has to sleep for real, because with a faked `asyncio.sleep` both versions report roughly zero.
    - **The pace is an interval *between* requests, so the first one never waits.** It reserves the cursor and goes; the second sleeps. `_reserve_pace_turn` is synchronous by construction — no `await` between reading the cursor and writing it back — which is what stops four slots on one lane reading the same "next allowed" moment and leaving together. A cancelled sleep gives its turn back: cancellation reaches a running sync, and the cursor is the one piece of state here with no self-correcting path.
    - **The wait is served *before* the lane permit, not while holding it.** The first cut held it, arguing the permit is what serialises the egress. That was wrong twice over: the cursor already spaces the starts, so the permit added no pacing at all, while holding it parks every *other* kind of traffic on that proxy behind the sleep — at `PACE_MAX_MS` on a one-slot lane, four requests per `ACQUIRE_TIMEOUT_SECONDS`, so thumbnails and publishes start failing with `ProxyLaneUnavailable`. Precisely what ticket 13's `hold()` docstring forbids, reintroduced by the sleep rather than by the walk. **The guard is inverted, not deleted.** Serving it early means the egress must be known before the acquire (`ProxyPoolManager.peek_lane_url` — exact for a bound worker, advisory for free choice), which also fixes the attribution of a failure *during* the acquire: it used to be filed against the `"direct"` egress on a deployment that has none.
    - **A full lane queue is not a proxy fault.** `_proxy_acquire` translated `ProxyPoolExhausted` into a bare `ConnectionError`, which the old rule filed with the dead proxies. That becomes self-reinforcing the moment pacing lands: a paced lane is exactly what makes its own queue deep enough to reach `ACQUIRE_TIMEOUT_SECONDS`, so the mechanism would manufacture the cooldown it exists to replace and blame a healthy proxy on the way. It is now `ProxyLaneUnavailable`, still a `ConnectionError` subclass so nothing above notices.
    - **Two constants, and the one that needed re-deriving was not the obvious one.** `_NO_HEALTHY_WORKER_WAIT_SECONDS` stays 5.0: it bounds the wait for a *free and healthy worker*, and a worker serving a paced fetch is **busy** — not free, not parked — so pacing lengthens the message a worker is already running, which the drain sees through `all_busy()` as ordinary backpressure. Deriving it from `PACE_MAX_MS` would park every empty-queue sweep for thirty seconds for nothing. Its guard needs a worker with a **real lane**: `proxy_url` is None for a laneless one and `is_parked` short-circuits on that, so the first version passed against its own mutation. **`_worst_case_fetch_seconds` did need it** and was missed on the first pass — every attempt may sleep up to `PACE_MAX_MS`, so a call against a proxy at the ceiling is `NETWORK_FETCH_RETRIES x PACE_MAX_MS` longer (240s, ~+28%), and `visibility_timeout_seconds` is built on that number. A VT that under-counts is PGMQ redelivering a message a live worker is still walking, which is decision 32's double-scrape. The 2x factor was absorbing it, so the failure was a silently shrinking margin. Its guard pins the pace term **exactly** rather than as a lower bound, because the backoff term alone (381s) already exceeds it and the loose version survived its own mutation.
    - **Only the web view is paced, and only it supplies signals.** The same `is_telegram_web_url` predicate the quota ledger uses. The Bot API travels the same proxies and answers to different limits, so a publish made to wait thirty seconds because the *web view* is throttled punishes the wrong request — and taking the signal from it would file another service's 429 against this egress's pace.
  - **Ownership is granted by `claim_job`, never by creating a job.** `create_job` runs wherever the request landed, so while it wrote to `_active_jobs` the API believed it owned every sync it created — `get_job` served its own stale object and `apply_progress_event` discarded the worker's deltas as an echo, leaving the stream at `pending` with no `[DONE]` and nothing in error. Only the consumer claims, as it starts a Channel; `_remember` keeps a watcher's reference current without claiming, and caps the mirror at `MAX_MIRRORED_JOBS` because evicting one costs a row read, never correctness.
  - **Scheduler status crosses the split in both directions.** `_job_status` is filled in by whichever process runs the jobs, so `GET /jobs/status` would report `idle`/`null` forever; the worker announces each transition on `scheduler_job_status` and the API folds it in. `POST /jobs/{id}/trigger` **rings** the worker (`request_job_run`) instead of running the runner locally — the alternative is the API tier sweeping retention and fetching `t.me` for a probe sweep on a button press. Announcing is best-effort and swallows its own failures: a job must not be able to fail because its own description could not be sent.
  - **Progress crosses processes over `LISTEN`/`NOTIFY`** (`app/core/pg_notify.py`; *enforced: `tests/services/test_cross_process_progress.py`*). The failure this prevents is silent: `sync_job_events` already falls back to `get_job`'s row read, so a sync in another process would keep streaming and just serve 5-second-old state. The notification therefore carries **the changed Channel**, not only the job id — the row stays on its crash-recovery cadence and the watcher patches a mirror. Cancellation travels the same channel in the other direction, because the `asyncio.Event` the sync polls lives in the worker while `POST /jobs/sync/{id}/cancel` runs in the API.
- **Never hold a session open across `await`ed work.** A transaction left `idle in transaction` pins the xmin horizon, so autovacuum reclaims nothing for as long as it lasts: `run_auto_sync` planned and synced inside one `with Session(engine)` and left `tg_sync_meta` with **10 live rows and 4,743 dead** after 1,062 autovacuums. The symptom is not a slow query — it is single-row updates by primary key that are instant 99% of the time and stall for 21 seconds occasionally, with no I/O and nothing in `pg_blocking_pids`. Read what you need, project it to plain values, close the session, *then* do the slow thing.
- **Sync progress is pushed over SSE**, not polled: `POST /api/v1/jobs/sync` → `GET /api/v1/jobs/sync/{id}/events`. One-shot `GET .../{id}` is the reconnect fallback. The `tg_sync_jobs` row exists only for that fallback — there is **no list endpoint**, so job history is a write-only trail. It is pruned by `SYNC_JOB_RETENTION_DAYS` (a deployment constant, not an operator setting, precisely because nothing browses it) and **only in a terminal state**, so a long sync is never deleted from under a reconnecting client. That makes a job stranded by a restart immortal, which is why `reconcile_interrupted_jobs` runs at startup: in-memory progress does not survive the process, so every non-terminal row is provably dead. It had never been reconciled — 711 rows sat in `running` since June. Since ticket 10 it runs in **the worker's** startup and nowhere else, because the API restarting no longer says anything about whether a sync is alive. **Sound only while the sync tier is single-replica** (see the worker note above).
- **Three layers answer "why is this slow", and they are not interchangeable.** See **Finding slow endpoints** in `deployment.md`. Traefik's JSON access log is the only one that sees *transfer* cost (`backend/scripts/slow_endpoints.py` aggregates it, ranked by total time); `app/middleware/timing.py` gives `Server-Timing` plus a slow-request WARNING keyed by route template; `pg_stat_statements` names the query and its I/O. Reach for the edge log first — this project's bottleneck has moved off the backend before and every server-side number said it was fine. **But the edge log cannot see background work at all**, and after two rounds where it named the culprit it was tempting to stop there: with every endpoint under a second, `pg_stat_statements` still showed the auto-sync tick spending **69 minutes of database time per 10 hours** on stats it discarded (`docs/scheduler-db-cost-plan.md`). Nothing in the top ten by total time was a request. When the layers disagree about whether the system is busy, the one counting requests is the one that is blind.
- **A scheduled job pays its cost every tick, forever.** The endpoint rounds were each triggered by someone waiting; a job nobody is watching has no such signal, so the same "compute it for everything, read one field" defect ran for months. Before batching a computation across every row, check what the caller reads and *when it could possibly matter* — `sync_schedule.needs_dynamic_stats` is that check made explicit, and it took 2,077 channels down to six.
- **Compression is Traefik's job, not the app's.** Deployed responses are gzipped by a `compress` middleware declared on the `backend`/`frontend` service labels in `compose.yml` (see `deployment.md`). Do **not** add Starlette's `GZipMiddleware` to `app/main.py`: it would double-encode behind the proxy, and unlike Traefik it buffers, which *would* stall the SSE routes. `uv run fastapi dev` serves uncompressed — that is expected, and it is why payload sizes look different locally than in the browser against staging.

## Frontend architecture

- **Two API clients, split per *call* by contract (ADR-006).** *Enforced: `src/api/client-split.conform.ts`.* Generated `frontend/src/client/` (committed, do not hand-edit) for the admin/user shell **and** every summarizer call whose response type is at least as useful as a hand-written one. Hand-written `frontend/src/api/` for the rest: SSE streams, blob downloads, and calls whose generated type would be a *downgrade* — either an **open** model (`extra="allow"` → a top-level `[key: string]: unknown`, so `extra` keys arrive as `unknown`) or a **closed but all-optional** one (OpenAPI cannot say "has a default, therefore always present"). The split is per call, not per family: `jobs` has five generated and three hand-written. Measure openness with `string extends keyof T`, never by grepping for `[key: string]` — that also counts *nested* index signatures. After backend API changes, regenerate with `bash scripts/generate-client.sh` (runs with `ENVIRONMENT=production`).
- **Server state = TanStack Query, always.** *Enforced (partially): `src/lib/architecture-invariants.test.ts` pins `DataContext`'s field set, so server state cannot be re-added there.* `DataContext` derives from queries and exposes Dispatch-compatible setters as query-cache write-throughs (`hooks/useChannels.ts`, generic helper `lib/applySetStateAction.ts`); query keys in `hooks/queryKeys.ts`. Add new server state through react-query, not context `useState`.
- **PostgreSQL is the only client-side store.** *Enforced: `src/lib/architecture-invariants.test.ts`.* A4 deleted the IndexedDB mirror (−2,491 lines) — no `idb`/`localforage`/`dexie` dependency, no `indexedDB`, no DB worker. The browser keeps settings and the current selection, nothing else.
- **Nothing says `localStorage` except four modules.** *Enforced: `src/lib/architecture-invariants.test.ts`.* Browser storage is per-account: `lib/storage/scoped.ts` puts every key under `u:<userId>:`, where the id is the JWT `sub` claim **decoded client-side without verifying it** — the namespace is needed synchronously at first render, before `usersReadUserMe()` could resolve, and forging a token buys a prefix, not data. Use `scopedStorage`, never `localStorage`. Roughly thirty keys were bare names before ticket 02, so on a shared machine the second person to sign in inherited the first person's channel selection, filters and settings. The rule is "do not name `localStorage`" rather than "namespace your keys" because only the first can be checked: one forgotten `setItem` in a new hook re-opens the leak for that key silently, and the line looks exactly like the twelve around it.
  - **The four exceptions are device-scoped on purpose, and say why.** `scoped.ts` itself; `theme-provider.tsx` and `api/base.ts`, which read `vite-ui-theme` and `access_token`; and `useAuth.ts`, which owns the token every namespace is derived from. The token cannot be namespaced by the id inside it, and the theme is read by a provider that mounts above the router and renders `/login`, so namespacing it would flash the wrong theme on every sign-in. `DEVICE_SCOPED_KEYS` is asserted as an exact pair — a third entry is a decision, not a drive-by.
  - **Signing out clears the query cache, not just the token.** `logout()` removed the token and nothing else, so every channel, post and summary the previous person had loaded stayed readable until something happened to refetch. `clearStaleSession` had the same hole on the branch where the operator was already on `/login` and the hard `window.location.href` never ran. Stored *preferences* are deliberately **not** cleared: they are already unreachable to another account, and dropping them means signing back in to a reset app.
  - **Values written before the namespace existed are adopted once, by a sweep.** Not key by key at each call site — that only covers the keys somebody remembered. The sweep is marker-guarded per account and **moves** rather than copies, and it refuses to run for a signed-out browser, because filing the existing operator's settings under `u:anon:` would lose them. The first account to sign in after the upgrade therefore claims them; that is deliberate and argued in the module docstring.
  - **The guard matches the identifier, not `localStorage.`** — because `f(localStorage)`, `Object.keys(localStorage)` and the exact line this ticket deleted (`loadAppSettings(typeof window !== "undefined" ? localStorage : …)`) are all member-access-free. Comments and string literals are stripped first, so the prose can keep saying "localStorage" and one export document can keep it as a field name.
  - **A read can never throw.** The sweep writes from inside `getItem`, and `getItem` is called from `useState` initialisers — so a quota error, or Safari with site data blocked (`typeof localStorage` is still `"object"` there and every call throws), would white-screen the app on something that could not fail before. Every accessor swallows storage errors.
  - **Playwright seeds through `tests/utils/scoped-storage.ts`, never bare keys.** The guard only scans `src/`. A spec seeding `hasSeenTour` under its bare name does not merely fail to work — the guided tour opens over the UI and every later assertion in the file misses for reasons unrelated to what it tests. The helper computes the prefix by calling the app's own `scopedKey`, so the namespace format is declared once.
- **Settings = schema-driven.** All browser-persisted settings are declared in `frontend/src/lib/settings/schema.ts` (zod: key, default, legacy keys, backend section); `SettingsContext.tsx` is a thin provider over generated setters, reading and writing through `scopedStorage`. Add settings to the schema, not as new `useState` hooks. Theme is owned by `theme-provider` in `main.tsx` (`localStorage: vite-ui-theme`, declared once in `lib/storage/scoped.ts`) — do not add a second theme toggle (*that one is enforced*; the schema rule is **not** — be careful).
- **Routing/tabs come from the URL.** TanStack Router. The active summarizer tab is the `?tab=` param on `/summarizer` (not localStorage); settings sub-sections use `?section=`.
