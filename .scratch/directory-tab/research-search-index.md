# Directory keyword search: what to index and where

Research, 2026-10-04. Read-only: nothing in the app, database or staging changed. Two claims come from read-only probes on the local `postgres:18` container (PG 18.6, `en_US.utf8`) and are marked "checked locally".

## Answer

Stay on PostgreSQL's built-in full-text search, in a companion table that the Directory aggregate rewrites in the same transaction that replaces an entry's samples. Discourse, GitLab basic search, Synapse and Mastodon's account search all work this way. Each of them moves to a second engine only for scale or features this Directory does not need yet. Fix the prototype's language gaps in Python before `to_tsvector`, which is how Discourse handles Chinese with cppjieba. Pick the text search configuration per row from the entry's ADR-021 language, so Russian, English, German and Arabic get stemmed and every other language uses `simple`. Fold Persian letter variants and split on ZWNJ. Turn CJK runs into character bigrams. Add one small pg_trgm index over handle and display name so names match with typos. Build snippets for the result page only. Skip Elasticsearch, Meilisearch and Typesense on an 8 GB VM with 320K documents. If measured ranking quality or latency still falls short after this, ParadeDB (BM25, ICU and jieba tokenizers, AGPL, custom image) is the next step. Embeddings come later as a second ranked list merged by reciprocal rank fusion. They do not replace keyword search.

## Options compared

| Option | Mixed scripts (Cyrillic, Persian, CJK) | Ranking | Size and upkeep here | Ops cost on this stack | Maturity, license |
|---|---|---|---|---|---|
| tsvector `simple` (prototype) | No stemming. A Chinese run is one lexeme: `to_tsvector('simple','电报频道新闻')` gives `'电报频道新闻':1`, and ZWNJ stays inside Persian tokens (checked locally) | `ts_rank`, which reads the tsvector of every match | 1.8 GB measured | none | core |
| tsvector, per-row config plus Python normalisation (**recommended**) | PG 18 ships 30 configs (29 languages plus `simple`), including russian, english, german and arabic, but none for Persian, Ukrainian, Chinese or Japanese (checked locally). Those use `simple` plus pre-processing | same | about the prototype's size. Bigrams add tokens for about 10K CJK channels | none | core |
| pg_trgm | Works on any characters the ctype counts as alphanumeric. A 2-char CJK word has no trigram, and "a pattern with no extractable trigrams will degenerate to a full-index scan" ([docs F.35.4](https://www.postgresql.org/docs/18/pgtrgm.html#PGTRGM-INDEX)) | similarity only | small over names. Large over 5 GB of samples (not measured) | contrib, already available in the image (checked locally) | core |
| pg_bigm | Built for CJK, with fast 1–2 character searches ([comparison table](https://github.com/pgbigm/pg_bigm/blob/master/docs/pg_bigm_en.md)) | `LIKE` only | GIN | not in PGDG trixie for PG 18 (checked 2026-10-04), so build from source | PostgreSQL license, last tag v1.2-20250903 |
| PGroonga | all languages, CJK included ([site](https://pgroonga.github.io/)) | Groonga score | stores its index outside PG's WAL. Crash safety needs `pgroonga_crash_safer` preloaded and costs write speed ([crash-safe](https://pgroonga.github.io/reference/crash-safe.html)) | custom image, Groonga's apt repo | PostgreSQL license, 4.0.9 (2026-09-23) |
| ParadeDB `pg_search` | ICU, jieba and lindera tokenizers. Snowball stemmers for russian and arabic, not Persian ([stemming](https://github.com/paradedb/paradedb/blob/main/docs/reference/token-filters/stemming.mdx)) | BM25 | its own segment index | custom image. | RUM | same as tsvector | can order by rank from the index | "slower build and insert time" and generic WAL ([README](https://github.com/postgrespro/rum)) | `postgresql-18-rum` in PGDG | PostgreSQL license |

| Elasticsearch / OpenSearch | Chinese needs the `ik` plugin ([Mastodon docs](https://docs.joinmastodon.org/admin/elasticsearch/)) | BM25 | memory "can easily outpace those of Mastodon itself" (same page) | JVM service | OpenSearch Apache-2.0 |

## What the projects do

**Discourse** keeps `<table>_search_data` rows holding `raw_data`, a `search_data` tsvector built with `setweight` A–D, `locale` and `version` ([search_indexer.rb L32–56](https://github.com/discourse/discourse/blob/67bc74d0d83f/app/services/search_indexer.rb#L32-L56)). Indexing runs on save through `SearchIndexer.index` ([L280](https://github.com/discourse/discourse/blob/67bc74d0d83f/app/services/search_indexer.rb#L280)). A background reindex sets `version` to `REINDEX_VERSION = 0`, and a job walks the stale rows ([L244–278](https://github.com/discourse/discourse/blob/67bc74d0d83f/app/services/search_indexer.rb#L244-L278)). The configuration is chosen once per site from `default_locale`, and unlisted languages fall back to `simple` ([search.rb L42–83](https://github.com/discourse/discourse/blob/67bc74d0d83f/lib/search.rb#L42-L83)). Chinese is segmented with cppjieba and Japanese with TinySegmenter, both in Ruby before `to_tsvector` ([L127–163](https://github.com/discourse/discourse/blob/67bc74d0d83f/lib/search.rb#L127-L163)). Ranking is `ts_rank_cd` multiplied by category weights ([L1350–1450](https://github.com/discourse/discourse/blob/67bc74d0d83f/lib/search.rb#L1350-L1450)), the same relevance-times-business-weight shape as the prototype. Excerpts are cut from `raw_data`, and `use_pg_headlines_for_excerpt` is off by default ([site_settings.yml L3789](https://github.com/discourse/discourse/blob/67bc74d0d83f/config/site_settings.yml#L3789)). Discourse also caps duplicate positions per lexeme to keep tsvectors small ([search_indexer.rb L116](https://github.com/discourse/discourse/blob/67bc74d0d83f/app/services/search_indexer.rb#L116)).

**GitLab basic search** uses the same companion-table pattern. `issue_search_data` is partitioned by hash on `project_id`, and every partition's GIN index is created `WITH (fastupdate='false')` ([structure.sql](https://gitlab.com/gitlab-org/gitlab/-/raw/6aaca3b6e85d/db/structure.sql)). Rows are rewritten in `after_save_commit` with the `english` configuration, capped at 1 MB, with long tokens stripped first ([pg_full_text_searchable.rb](https://gitlab.com/gitlab-org/gitlab/-/blob/6aaca3b6e85d/app/models/concerns/pg_full_text_searchable.rb)). Partial matching needs 3 characters ([pattern.rb](https://gitlab.com/gitlab-org/gitlab/-/blob/6aaca3b6e85d/lib/gitlab/sql/pattern.rb)). Advanced search runs on Elasticsearch ([docs](https://docs.gitlab.com/user/search/)). GitLab's infrastructure team once found 400,000 pending GIN pages on a trigram index and disabled `fastupdate` on it ([issue 1908](https://gitlab.com/gitlab-com/gl-infra/scalability/-/issues/1908)).

**Synapse** writes `to_tsvector('english', ?)` into `event_search.vector` when the event is stored, queries with `websearch_to_tsquery`, ranks with `ts_rank_cd`, and runs `ts_headline` only on returned events ([search.py L90, L472, L772](https://github.com/element-hq/synapse/blob/4f5524043c40/synapse/storage/databases/main/search.py#L90)). It applies English stemming to every language.

**Mastodon** searches accounts in Postgres with `simple`, A/B/C weights and a trailing `:*` on the final term ([account/search.rb L10–12, L146–151](https://github.com/mastodon/mastodon/blob/79f21a20736b/app/models/concerns/account/search.rb#L10-L12)). Statuses are searchable only through Elasticsearch, fed by an asynchronous Redis queue that a scheduler drains in batches of 1,000 ([indexing_scheduler.rb](https://github.com/mastodon/mastodon/blob/79f21a20736b/app/workers/scheduler/indexing_scheduler.rb)).

**Lemmy** runs `ILIKE '%a%b%'` over GIN trigram indexes on names and bodies ([migration](https://github.com/LemmyNet/lemmy/blob/8d83bcf176e5/migrations/2023-07-24-232635_trigram-index/up.sql), [fuzzy_search](https://github.com/LemmyNet/lemmy/blob/8d83bcf176e5/crates/diesel_utils/src/utils.rs#L144-L151)) and sorts by hot or new rather than by relevance.

**Mattermost** builds a GIN index on `to_tsvector('english', message)` ([migration 000234](https://github.com/mattermost/mattermost/blob/af4c3cfde668/server/channels/db/migrations/postgres/000234_recreate_posts_message_txt_index.up.sql)). When a query contains CJK it falls back to `LIKE`, and the code comment explains why it skipped pg_bigm: it is a third-party C extension that some managed services do not offer ([post_store.go L2320–2330](https://github.com/mattermost/mattermost/blob/af4c3cfde668/server/channels/store/sqlstore/post_store.go#L2320-L2330)). Database search is meant for "under about 2–3 million posts". Bleve was removed in v11, leaving Elasticsearch or OpenSearch ([enterprise search](https://docs.mattermost.com/administration-guide/scale/enterprise-search.html)).

**Supabase** documents hybrid search as tsvector plus pgvector merged by RRF with `k = 50`, where each side contributes `least(match_count, 30) * 2` candidates ([hybrid search](https://supabase.com/docs/guides/ai/hybrid-search)). For CJK it recommends PGroonga ([guide](https://supabase.com/docs/guides/database/extensions/pgroonga)).

## Recommended design

**Table.** `tg_channel_directory_search`: `handle` PK and FK to the entry with `ON DELETE CASCADE`, `ts_config regconfig`, `tsv tsvector`, `names text` (lowercased handle plus display name), `index_version smallint` and `indexed_at`. It is `Scope.CORPUS` like the entry and is owned by the `channel_directory.py` aggregate as its payload table. That keeps the big tsvector off the entry's list reads, which is the repo's companion-table rule. Indexes: `GIN (tsv) WITH (fastupdate = off)` as GitLab does, and `GIN (names gin_trgm_ops)`. Only live channel entries get a row. Any other verdict deletes it.

**Document.** Weight A is handle and display name, B is the bio, C is the 8 newest samples capped at 12,000 characters, with Discourse-style capping of positions per lexeme. The configuration comes from `language`: ru, en, de and ar map to their built-in configs, and every other language maps to `simple`. A generated column cannot do this, because a generation expression cannot "reference anything other than the current row" ([docs 5.4](https://www.postgresql.org/docs/18/ddl-generated-columns.html)). Python normalises the text before it reaches Postgres. Persian ی/ک fold to Arabic ي/ك so the arabic stemmer still applies, tatweel and harakat are removed, and ZWNJ becomes a space. CJK runs become overlapping character bigrams, the approach Elasticsearch's `cjk_bigram` filter takes ([docs](https://www.elastic.co/docs/reference/text-analysis/analysis-cjk-bigram-tokenfilter)), and no dictionary is needed.

**Update path.** Rebuild the row synchronously inside the writers that already change its inputs: `record_probe_result` (samples replaced), `record_sync_metadata` (name and bio), the recheck path, and sample retention. This avoids triggers. Twenty sample deletes and inserts plus an entry update would fire a trigger several times per probe, and Postgres has no CJK segmenter to run inside one. An asynchronous queue, as Mastodon uses, is not needed either: a weekly refresh of 320K entries averages about 0.5 rebuilds per second, all in the same database. Discourse's `index_version` idea stays: raising it lets a backfill walk re-index stale rows after the recipe changes. For the first fill, load the rows in batches, then build the GIN index with a large `maintenance_work_mem` ([GIN tips](https://www.postgresql.org/docs/18/gin.html#GIN-TIPS)). Add a guard in the style of ADR-015 asserting that every writer leaves `tsv` equal to a fresh rebuild.

**Query.** Python normalises the input the same way. Every term except the last is matched as a complete word. The last term gets `:*` once it reaches 3 characters, following Mastodon and Discourse's default `min_search_term_length` of 3. Because rows use different configurations, each term becomes `to_tsquery('simple',t) || to_tsquery('russian',t) || to_tsquery('english',t) || ...` over the configs in use, and the terms are joined with AND. A CJK term becomes bigrams joined with AND. The query:

```sql
SELECT e.handle, ts_rank(s.tsv, $q, 1) * ln(10 + coalesce(e.subscribers, 0)) AS score
FROM tg_channel_directory_search s JOIN tg_channel_directory e USING (handle)
WHERE s.tsv @@ $q AND <numeric filters>
ORDER BY score DESC LIMIT 50;
```

Count results with a capped subquery (`LIMIT 1001`, shown as "1000+"). Match names by OR-ing in `s.names % $raw` or `ILIKE` on the trigram index, which gives typo tolerance and CJK name matching.

**Snippets.** Build them for the 50 rows on the page only, as Synapse does and ParadeDB's docs advise ("recommend passing a `LIMIT`", [highlight](https://github.com/paradedb/paradedb/blob/main/docs/reference/full-text/highlight.mdx)). Postgres warns that `ts_headline` "uses the original document ... so it can be slow" ([12.3.4](https://www.postgresql.org/docs/18/textsearch-controls.html#TEXTSEARCH-HEADLINE)). Cut them in Python from the same normalised sample text, highlighting words that begin with each stemmed query lexeme. This follows Discourse's `raw_data` excerpts, and it works for bigrams and Persian, where `ts_headline` on raw text would not match.

**Container.** Set `shm_size` on the db service. Docker's 64 MB default makes parallel queries fail with "could not resize shared memory segment" ([image docs](https://hub.docker.com/_/postgres)).

**Semantic search.** Add it later as a complement. ADR-005's JSON-plus-numpy approach does not scale to 320K vectors per query, so it would need `postgresql-18-pgvector`, which is in PGDG, and an ADR superseding ADR-005. Merge the two lists by RRF following Supabase's recipe. Meilisearch's docs give the same advice for multilingual data: use "hybrid search with a multilingual embedder alongside localized attributes". Under ADR-016 the embeddings run on the Operator Key, because the rows are shared.

## Open risks

- The prototype's 0.2–2.7 s has not been broken down. If `EXPLAIN (ANALYZE, BUFFERS)` shows the time going to detoasting tsvectors for `ts_rank` on broad prefixes, try RUM, then ParadeDB.
- Querying with an OR across configurations adds one GIN probe per config and term. Measure it with 5 configs before adding more.
- A Russian channel that posts in Ukrainian gets stemmed as Russian. Finglish is misdetected (ADR-021). Both still match by prefix.
- Bigrams over-match Japanese kana. If that matters, use the jieba or lindera segmenters Discourse and ParadeDB use.
- Every refresh rewrites the row, so the table turns over weekly. Tune autovacuum per table.
- ParadeDB is AGPL, still 0.x (v0.26.0 on 2026-10-03), and added a pgvector dependency in 0.25.0. Pin the version if you adopt it.
